# Ruling WA-DEPLOY-2

**Decision (Ahmad, 2026-11-02; replaces WA-DEPLOY-1):** ebda-whatsapp deploys from GitHub CI the same way ebda-store does. `cf-deploy.yml` runs on every push to `main` and on `workflow_dispatch`, on `ubuntu-24.04` pinned in the YAML (never a repo variable, Ruling RUNS-ON-NEVER-1), in the `production` environment, with `CLOUDFLARE_API_TOKEN` held as an environment secret. It calls the one deploy path, `scripts/deploy.sh` (account guard, commit-is-on-main guard, D1 migrations, `wrangler deploy`, then `verify-prod`: live commit, headers, webhooks, cron), and pages Telegram when it fails. A PR that edits `cf-deploy.yml`, `deploy-change-label.yml`, `scripts/deploy.sh`, `scripts/verify-prod.mjs`, `scripts/ci/deploy-change-label.mjs` or `wrangler.jsonc` needs Ahmad's `deploy-change` label (`deploy-change-label.yml`, Ruling DEPLOY-PARITY-1). Nobody deploys from the Mac any more: no local `scripts/deploy.sh`, no local build (MAC-LIGHT-1).

**Evidence:** WA-DEPLOY-1 kept the token off GitHub because the Free plan has no environment protection, so a branch with an edited workflow could read a secret. The label check is the human checkpoint that replaces it for the files that decide what reaches production, and it is the pattern ebda-store already runs. The first deploy of this repo through CI replaces the Mac deploy of 2026-11-02 (31c352a).

**Cost if wrong:** a deploy-file change merged without a careful read can exfiltrate the Cloudflare token (it can deploy arbitrary code to the live Worker and read or write D1, R2 and the queues); a push to main now deploys without a human dispatch, so a bad merge reaches production in minutes (rollback: `docs/runbooks/rollback.md`).

**RESIDUAL (accepted, Ahmad 2026-11-02; the same residual exists in ebda-store).** The `deploy-change` label check is advisory, not a gate: it runs PR code, so a PR that edits the label workflow or script can make it pass. On the Free plan the `production` environment has no required reviewer and no branch rule, so `CLOUDFLARE_API_TOKEN` is reachable by any workflow on any branch that a person with write access pushes (for example a workflow that names `environment: production`). We accept this because only Ahmad and his agents have write access to this repo. Interim hardening: the deploy job runs only when `github.ref == 'refs/heads/main'`, and no workflow that references the token may have a `pull_request` or `pull_request_target` trigger (`test/deploy-workflow.test.ts` checks both). The real fix is CF-BUILDS-1: deploy with Cloudflare Workers Builds so no Cloudflare token lives in GitHub at all (queued separately, not built here). Cost if wrong: anyone who gains write access to the repo can read the token and deploy arbitrary code to the live Worker and read or write D1, R2 and the queues; rotate the token at once if a collaborator is ever added or a write credential leaks.
