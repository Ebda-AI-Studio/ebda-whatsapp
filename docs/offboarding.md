# Workspace deletion (OFFBOARD-1, iceberg B2 / M-042)

An owner or an operator can delete a workspace. Nothing is deleted at once: a **14-day cooling-off** gives the owner time to change their mind. After it a resumable job erases everything the merchant put here and keeps only the money records the law requires.

## API
| Who | Call | Notes |
|---|---|---|
| Owner | `POST /api/v1/stores/:id/offboarding` `{ confirm: true, acceptWriteOff?, reason? }` | 202 with the status. `confirm` must be literally `true`. The owner cannot skip the wait (a strict schema: `immediate` is a 400). |
| Owner | `GET` / `DELETE /api/v1/stores/:id/offboarding` | status / cancel (only while `pending`). A suspended workspace may still POST and GET, never DELETE. An owner cannot cancel a deletion an operator started: `403 operator_requested` (the help guide tells them to write to support). **Starting and cancelling through this route are the OWNER's alone**: a super admin gets `403` (GET is allowed); operators use the routes below, which need a reason and are audited. |
| Operator | `POST /api/v1/operator/workspaces/:id/offboarding` `{ reason, immediate?, acceptWriteOff? }` | A reason (5+ characters) is required. `immediate` skips the cooling-off (a legal request). Asking again can only shorten the wait. |
| Operator | `DELETE .../offboarding` `{ reason }`, `GET .../offboarding`, `GET /operator/offboardings?state=`, `POST /operator/offboardings/run` | cancel, read, list, finish an interrupted run now. |
| Operator | `POST .../offboarding/approve` `{ reason }`, `POST .../offboarding/release-hold` `{ reason }` | the second approval of an immediate deletion that writes off >= 1,000 EGP (OFFBOARD-2ND-APPROVER-1); lifting the abuse hold (OFFBOARD-ABUSE-1). |

A NEGATIVE wallet (a debt) never blocks the erasure of data, but is preserved: the `suspend` step writes one `offboarding_log` row `debt_preserved` (`debt_minor=N`), the kept ledger copy keeps the balance, P1 `offboarding_debt_outstanding` fires, and nothing is written off or refunded against it (WA-DEBT-1). A wallet balance above zero is refused (`409 wallet_balance_remains`) unless the request carries `acceptWriteOff: true`; the amount is recorded in `offboarding.write_off_minor`. Refund it first through the normal refund path if the merchant wants the money back (WA-REFUND-1 applies to a cancelled plan).

An operator asking while an owner request is pending TAKES IT OVER in one conditional statement (role, requester, reason, the earlier of the two dates, the write-off), so the owner can no longer cancel it; an owner asking never downgrades an operator-owned row. Every change writes exactly ONE `offboarding_log` row in the same batch (`taken_over` or `operator_changed`, detail = previous and new values plus `taken_over` / `expedited` flags); a request that changes nothing writes nothing. The wallet balance is read again: if it grew beyond the write-off the owner accepted, the operator gets `409 write_off_required` with `amountMinor` and must pass `acceptWriteOff: true` (the new amount replaces the stored one and is in the log).

## Screens
- **Owner**: Wallet screen, last card "Delete this store's WhatsApp account" (`OffboardingCard`): what happens, the wallet balance and a tick to give it up (shown in money; confirm stays off until ticked), the cooling-off date once asked, a cancel button, and, when our team started the deletion, no cancel button but "Our team started this deletion. Write to us at <supportEmail>" (the brand's `supportEmail`).
- **Operator console**: tab "Delete a workspace" (`OffboardingOpPanel`): store id + reason (5+ characters), "Request deletion in 14 days", "Delete now" (immediate), the write-off tick when the server answers `write_off_required` (with the amount), cancel, the status (state, steps done, last error), the request's log, and the list of all requests.

## Race safety (security review)
The run is claimed with ONE conditional write (`state IN ('pending','running') AND execute_after <= now`, `meta.changes` checked); a row cancelled or not yet due since it was read is `skipped`. The state is re-read (`running`) before EVERY step, so a cancel that lands mid-run stops before the next destructive step. Cancel itself only succeeds on `pending`, so once the claim wins the deletion is irreversible by design.

## What the run does (daily cron, or "run now")
Steps are idempotent and recorded in `offboarding.steps_done`; a failed run resumes at the failing step (alert `offboarding_failed`, P1) and a finished one is a no-op.
1. **hold check** (before anything is touched; `last_error = held:<reason>`, alert `offboarding_held` P1 once, retried daily):
   - `open_refund`, `open_card_refund`, `payment_in_flight`: ANY open money row however old: a refund, a card refund, a top-up or package order still `pending`, a package order `paid` and not granted, an InstaPay request awaiting proof / under review / confirmed and not granted (OFFBOARD-HOLD-2: the age windows are gone; a late confirmation would otherwise credit a deleted workspace).
   - `suspended_abuse`: the workspace is suspended for any reason other than this deletion's own, and no operator released it (OFFBOARD-ABUSE-1).
   - `second_approval_required` (OFFBOARD-2ND-APPROVER-1).
   - `balance_grew`: the wallet balance is read again here AND once more right before `wipe_do`; if it is above `write_off_minor` nothing is erased (OFFBOARD-BALANCE-1).
2. `suspend`: D1 + the workspace's own copy.
3. `unroute`: the workspace's numbers, funding and **WhatsApp business tokens** are deleted first, so a late webhook finds no workspace.
4. `shared`: parked platform-number messages for customers only this store wrote to, then its routing rows.
5. `wipe_do`: Vectorize vectors, sockets closed, alarm cancelled, ALL Durable Object storage erased, one tombstone left (a stray call can never recreate the schema).
6. `r2`: `bodies/`, `media/`, `uploads/`, `imports/`, `instapay-proof/` under the workspace id (up to 20,000 objects per prefix per run; more continues next pass).
7. `backups`: `backups/<id>/` in the backup bucket. The wipe first marks the workspace as closing (no new alarm run or snapshot starts) and WAITS for a backup or alarm run already in flight; the `d1` step lists `backups/<id>/` once more before the batch.
8. `d1`: one batch. Subscription, store-plan and shared-number rows are deleted. Money rows stay (below). The workspace row is replaced by a tombstone under the pseudonym and removed.

## Review rulings (final review of PR #37)
**Ruling OFFBOARD-BALANCE-1 - a balance that grew after the write-off was accepted is never erased silently.** The run holds with `held:balance_grew` (P1) before `wipe_do`; it resumes only after an operator accepts the new amount (`acceptWriteOff: true`, audited) or the owner cancels (while `pending`). Evidence: `test/offboarding-review.test.ts` ("0 -> pending -> a 2,000 EGP credit"). Cost if wrong: a deletion waits for a person when a small credit (an adjustment, a repaired top-up) lands; the owner is never told "deleted" while money they did not agree to give up is gone.
**Ruling OFFBOARD-FREEZE-1 - once a deletion is `pending` or `running`, new top-ups, InstaPay requests and package purchases are refused (`409 offboarding_pending`); the owner cancels the deletion first if they want to buy.** Chosen over "refuse only while running": the 14 days are exactly when a balance can grow unseen, and the owner has a one-click way out. Refunds and operator adjustments are not blocked (they are how money leaves). Cost if wrong: an owner who asked for deletion and changes their mind must cancel before topping up (one extra click, and the cancelled request starts no timer).
**Ruling OFFBOARD-LATE-CREDIT-1 - money that reaches a deleted workspace is refused, alerted and refunded by hand; the pseudonymous workspace is never addressed.** Every credit/grant/charge path (`credit`, `grantOrder`, operator adjustments, provider refund debits) first asks `refuseIfOffboarded` (`src/core/ops/offboarded.ts`: the id is `del_<32 hex>`, or the deletion is `done`, or `wipe_do` is done). A refused one raises `credit_after_offboard` (P1), writes `billing_audit` once and leaves the order unpaid; no `WORKSPACE_DO.get(idFromName('del_...'))` happens, so no ghost workspace. Evidence: "a simulated late confirmation on an offboarded workspace". Cost if wrong: a provider confirmation arriving after deletion needs a human refund instead of a silent credit to nobody.
**Ruling OFFBOARD-HOLD-2 - the hold covers every open money row regardless of age (replaces the 2-day / 7-day windows of OFFBOARD-HOLD-1).** An abandoned pending checkout is moved to `expired` by the daily sweep after 7 days (top-ups) or the order expiry window, so it stops holding; an expired or failed row can still be confirmed late, which `OFFBOARD-LATE-CREDIT-1` covers. Cost if wrong: a pending checkout that no sweep expires holds a deletion until an operator rejects it.
**Ruling OFFBOARD-ABUSE-1 - a workspace suspended for abuse keeps its evidence: the run holds (`held:suspended_abuse`, P1) until an operator releases it with a reason (`abuse_hold_released` in `offboarding_log`).** Our own suspension step (reason `offboarding`) never holds. Cost if wrong: a legal-erasure request on an abusive account waits for an operator; the erasure deadline is the operator's to watch.
**Ruling OFFBOARD-2ND-APPROVER-1 - an immediate (cooling-off skipped) operator deletion whose write-off is >= `ADJUSTMENT_APPROVAL_MINOR` (default 1,000 EGP, the same threshold as the InstaPay two-approval rule) needs a SECOND operator.** The approver must differ from the requester and from everyone who touched the request or released a hold on it (`involvedActors`); the approval is bound to the exact execute-after, write-off and requester, so any later change voids it. An approval row by someone in that set is IGNORED when the run reads it (not only refused when written), and an operator who already approved cannot release the abuse hold (`approver_cannot_release`). The check runs against the row as it is NOW before every step after `suspend`, so a write-off raised while the run is in flight (the `write_off_accepted` path) needs a fresh second approver before anything is wiped. The 14-day path needs no approval (the cooling-off is the control). The request answers `needsSecondApproval: true`; the console shows an Approve button. Cost if wrong: an urgent legal deletion with a big balance waits for a second person.
**Ruling OFFBOARD-DAILY-1 - the daily pass pages by KEYSET `(execute_after, workspace_id)` through `drainKeyset` (M-178 class); held rows are visited once per pass and never starve a due one; `offboarding_backlog` (P1) when it stops with rows left.** Cost if wrong: none beyond the extra D1 reads.

## What is kept, and why
`src/core/ops/offboarding.ts` `OFFBOARD_TABLES` decides every D1 table that names a workspace (a test walks the schema, so a new table fails CI until someone decides).
- **Audit log actors (AUDIT-RETENTION-1)**: in the SAME `d1` batch, `audit_log.actor` of the workspace's owner/staff rows becomes the same pseudonym (operators and integration clients stay), through the controlled procedure that drops and re-creates the append-only triggers inside the batch (`src/core/ops/audit-retention.ts`). `audit_reasons` (the free-text reasons of operators and owners, including the ones behind `offboarding_log` rows) is deleted with the workspace; `offboarding_log` holds only the `reason_id` (D1 migration 0023), never text, and `offboarding.reason` is cleared when the run finishes or the request is cancelled (AUDIT-REASONS-1, which now covers every append-only table).
- **Money records (tax, refunds, disputes)** `topups, package_orders, package_refund_plans, instapay_requests, instapay_auto_confirmations, refund_requests, card_refunds, wallet_adjustments, shared_number_usage`: `workspace_id` becomes a **keyed-HMAC pseudonym** `del_<32 hex>` (HMAC-SHA-256 over the id, key HKDF-derived from `TOKEN_ENC_KEY`, label `offboard-pseudonym/v1`), the merchant's user id in `created_by` / `requested_by` becomes the same pseudonym, free text (`note`) and the InstaPay proof reference are cleared. Amounts, dates and operator ids stay.
- **Immutable ledgers** `ledger_mirror`, `billing_audit` (UPDATE/DELETE are blocked by trigger) and the **audit trails** `operator_actions`, `offboarding`, `offboarding_log`, `operator_view_log` (who viewed a workspace as the merchant: no text, the typed reason lives in `audit_reasons` and goes with the workspace) keep the opaque workspace id. `waba_signup_users`, `workspace_notices` (0029), `workspace_owners` and `new_cap_usage` (0030) are in `OFFBOARD_TABLES.delete` (they name the workspace and go with it). `meta_deletion_requests` (0026) has no workspace column: it concerns a Meta user (only a hash is kept), not a workspace, so it is outside `OFFBOARD_TABLES` on purpose.
- Everything else (numbers, tokens, subscriptions, routing, all DO data, all R2 objects) is deleted.

**Ruling OFFBOARD-AUDIT-1 - immutable ledgers and audit trails keep the opaque workspace id; they cannot be pseudonymised.** Evidence: database triggers `ledger_mirror_no_update`, `billing_audit_no_update`, `operator_actions_no_update`. The id is a random identifier that names nobody once the workspace row, the DO and R2 are gone; the name lives in the Store, not here. Cost if wrong: a regulator who holds both the Store's mapping and these rows can link the money back to the store; if that is ever required to be impossible, the triggers need a new migration that allows an offboarding-only rewrite.

**Ruling OFFBOARD-PROOF-1 - InstaPay proof images are deleted with the workspace; the request row (amount, reference, deciders, dates) stays.** The bank statement is the evidence of the transfer. Cost if wrong: a dispute about one transfer cannot be settled from the image; ask the merchant's bank.

**Ruling OFFBOARD-HOLD-1 - money in flight holds the run instead of cutting it off.** Cost if wrong: a merchant who abandons a refund request keeps the deletion waiting until an operator rejects it.

**Ruling OFFBOARD-KEY-1 - a deletion is refused (`no_key`) when `TOKEN_ENC_KEY` is missing.** It is a required secret; without it money records could not be pseudonymised. Cost if wrong: none (the secret is checked by `/health`).

## Audit
`offboarding_log` (append-only): `requested`, `taken_over`, `operator_changed`, `write_off_accepted`, `second_approval`, `abuse_hold_released`, `cancelled`, `started`, `step_done` (step name and counts), `completed`, with actor and a `reason_id` pointing at `audit_reasons`. No free text, phone number or message text is ever written; the operator view joins the reason in while the workspace exists.

## Not covered here
The Store's own account deletion drives the owner path (it calls the same endpoint through the owner's session); there is no Store-to-WhatsApp event for it yet.
