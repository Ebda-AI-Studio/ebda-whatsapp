# Ruling WA-DEPLOY-3

**Decision (Ahmad, 2026-11-02; replaces WA-DEPLOY-2):** ebda-whatsapp deploys through Cloudflare Workers Builds, connected to the GitHub repository, with the production branch `main`. No Cloudflare token or account secret exists in GitHub, and no GitHub workflow deploys. Workers Builds runs the build command `npm run build:web` and then the deploy command `bash scripts/deploy-cf.sh` on every push to `main`. The script refuses to run outside Workers Builds or on any branch but `main`, refuses the wrong Cloudflare account, applies the D1 migrations (`list`, then `apply --remote`), runs `wrangler deploy --var COMMIT_SHA:<sha>` and then `verify-prod` against the live Worker. Builds for non-production branches are switched off in the dashboard (the Worker uses Durable Objects, so a version upload gives no usable preview URL, and a preview build must never touch D1). `prod-verify.yml` is a dispatch-only read-only check of the live Worker with no secrets. A PR that changes any file outside the allowlist in Ruling GATE-INVERT-1 (everything except `src/**`, `web/src/**`, `docs/**`, root markdown, tests other than the label test, and brand image and font folders) needs Ahmad's `deploy-change` label, because those files decide what Workers Builds runs on the next merge. The exact dashboard settings are in `docs/launch/README.md` section 12.

**Evidence:** WA-DEPLOY-2 kept a Cloudflare token in a GitHub environment on a Free plan with no environment protection, so the token was reachable by any branch workflow of a person with write access (its recorded RESIDUAL). With Workers Builds the build token belongs to Cloudflare and never enters a GitHub runner, so that residual is gone. Cloudflare's documentation: Workers Builds runs the configured build then deploy command on the production branch, injects `WORKERS_CI`, `WORKERS_CI_BRANCH` and `WORKERS_CI_COMMIT_SHA`, and its default build token does not include D1, so the dashboard token needs D1 edit added for the migrations. `test/deploy-cf.test.ts` pins the order, the guards and that no workflow mentions a Cloudflare credential.

**Hardening and the residual (security review, 2026-11-02):** (1) builds for non-production branches are OFF in the dashboard; (2) the build token is scoped to the permissions listed in `docs/launch/README.md` section 12 and nothing else; (3) the build variable `NPM_CONFIG_IGNORE_SCRIPTS=true` is set, so no dependency install script runs with the token in the environment (verified: `npm ci --ignore-scripts`, `npm run build:web` and `wrangler deploy --dry-run` all succeed; only esbuild, workerd and sharp declare install scripts, and none is needed to bundle or deploy); (4) the deploy-change label is required for any changed file outside a short allowlist (Ruling GATE-INVERT-1: deny by default), with PostCSS pinned in `web/vite.config.ts` and a test that fails on any foreign lockfile. **Residual (accepted):** Workers Builds cannot scope a token to the deploy step only, so code that runs at build time (the build tool and its dependencies) shares the build token. It is limited by the lockfile pinning every dependency and by the label gate making Ahmad read any change to the lockfile or to any build, install or deploy file; the label check itself is advisory, as with any check that runs PR code.

**Cost if wrong:** the deploy now runs on every push to `main` without a GitHub-side check, so a bad merge reaches production in minutes (the merge gate and the PR CI are the only checks; rollback is `docs/runbooks/rollback.md`); a verification failure fails the build after the deploy has already happened; and a build token with too much access (D1, queues) is a Cloudflare-account secret, so keep its scope to the permissions in section 12.
