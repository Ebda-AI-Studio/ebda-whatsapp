# Billing (Phase 7)

The UI (wallet, operator console) is built against the DTOs in `src/core/api/contract.ts` ("Billing (Phase 7)" block); see "In the page" at the end. Amounts are integer piasters (EGP x 100); the currency is always EGP.

## Who pays Meta (WA-FUND-1)
`number_funding(phone_number_id, funding)` in D1, copied into each workspace.
- `merchant_card`: Meta bills the merchant's card. The wallet is NEVER debited for these numbers; the message's Meta cost is recorded (`billable_sends.cost_usd_micros`) and shown on the statement (`cardCosts`).
- `platform_line` (the plan calls it the Ebda line; `src/core/**` may not name the brand): the wallet pays. Used for the shared number.
- **Funding must be KNOWN.** A number with no row is `unknown` and cannot send (`funding_unknown`: API 409, queued message failed with that reason, campaign paused `funding_unknown`, alert). Nothing stamps a default: the code path that creates a number writes it (`recordNumberFunding` / `fundingStatement` in `src/core/billing/funding.ts`): own-number connect (Phase 8.1) writes `merchant_card` in the same batch as the `phone_numbers` insert; the shared-number setup (8.2, `POST /api/v1/operator/shared-numbers`, `docs/shared-number.md`) writes `platform_line` in the same batch as the `shared_numbers` row; a member workspace's funding copy includes the platform number while it is an active member; the operator can change it (`PUT /api/v1/operator/numbers/:id/funding`, audited; the owning workspace's copy is refreshed in the same request, so the next send already follows it). A miss triggers an eager re-pull (at most every 10 s) before refusing.
- The wallet also pays for AI credits (separate ledger, below).

## Money flow for a platform_line message
1. **Price inputs** (D1, immutable effective-dated versions): `rate_cards(ver, effective_from, country, category, usd_micros)`, `fx_rates`, `pricing_settings` (margin, overdraft, FX buffer, VAT), `workspace_pricing_overrides` (margin per workspace). Each workspace copies them lazily (<= 30 min old; a workspace that never pulled decides nothing: claims defer 60 s, the API refuses). Rate cards/FX are published >= 24 h ahead, settings/overrides >= 1 h ahead, so the copy always has a version before it applies.
2. **Pre-send** (at the API/Store-event queue for a refusal that writes nothing; at claim for everything): estimate = price by RECIPIENT market (calling code; unknown -> `ROW`) and category (a template's own category, everything else `service`) at the version in effect now. No price in effect -> refused `rate_unavailable` (never held at 0).
   - marketing: needs `available >= estimate` and no debt, else `wallet_empty` (a campaign pauses `wallet_empty`).
   - utility / service: may go down to `-credit_limit_minor` (default 50 EGP, WA-OVERDRAFT-1); beyond that they WAIT (<= 48 h, <= the 24 h window for free text): `wallet_wait` row, released FIFO when funds arrive, failed `wallet_empty_expired` at the deadline (fixed at the first wait).
   - authentication that cannot be paid fails at once (`wallet_empty`) so the Store falls back to e-mail.
   - `plan_blocked` (past_due / cancelled / expired, **or no entitlement row at all**: fail closed, a workspace the control plane has not pushed a plan to cannot send paid marketing) blocks marketing only; utility, authentication, service sends and inbox replies keep working. Evaluated by `marketingBlocked` (`src/core/billing/entitlements.ts`) at queueOutbound, queueTemplate, claim and campaign pages. Test workspaces get a version-0 baseline plan from the test helpers (`seedPlan`).
3. **Hold** `msg:<idempotencyKey>` (`wallet_holds`). `available = balance - held`. A campaign page reserves ONE parent hold `camp:<id>:p<n>`; its messages draw from it (no double reservation); the parent closes only when no message of the page is waiting.
4. **Meta statuses** carry `pricing {billable, pricing_model, category, type}`. `sent` + pricing re-estimates the hold to Meta's category. The FIRST `delivered`/`read` with a billable flag charges (`meta_charge`, ref `meta:<wamid>`, unique) at the rate/FX/settings version in effect at DELIVERY time. Not billable -> hold released. `failed` -> released. Non-PMP model -> `unpriced` alert, no charge. A later status naming another category posts the difference as `meta_adjust` (`adj:<wamid>:<category>`). No status within 31 days -> hold `expired` by the sweep; a late billable event still charges (the charge never needs a hold).
   - **No rate found at delivery** -> `pending_rate`: the hold STAYS; priced by the version in effect at delivery, else the earliest version after it, as soon as one arrives; after 7 days the held estimate is charged (alert). Never free.
   - WA-SHARED-FREE-1: service replies on a platform number are charged at the service rate whatever Meta's billable flag says; the `shared_number_trueup` task rebates the difference (below).
5. **Price**: `piasters = roundHalfEven(usd_micros x fx_micros x (10000 + margin_bps) x (10000 + fx_buffer_bps) / 10^18)` in BigInt, ONCE per row (the FX buffer adds to the plan's `/10^14` formula; with a zero buffer it is exactly that). VAT per row (`vat_bps`, 0 until Q5 is decided): `vat_minor = roundHalfEven(net x vat_bps / 10000)`. Statements sum stored rows; nothing is recomputed.

## Invariants (each has a test)
append-only ledger; `balance_after` chain; one charge per wamid under duplicate/out-of-order webhooks (incl. statuses before the accept); concurrent holds cannot exceed available; every terminal message path settles its hold (enqueue failure, opted-out drop, plan lapse, cancelled campaign, non-retryable failure, 131049 failure, rate-limited code, erasure, webhook failed, wait expiry, sweep); D1 mirror sum = DO sum after a drain; erasure leaves money intact; merchant_card numbers never debit; unknown funding / empty copy / missing rate never mean "free".

## Packages and entitlements (7.1)
`workspace_subscriptions(version)` in D1 -> `applyEntitlement` event (versions only move forward). Daily cron (`17 1 * * *`, the only cron) re-sends every subscription and repairs lost top-up webhooks. A new period grants `grant:<period_start>:<package>` AI credits and expires the last period's unused grant; an upgrade grants the difference. The Store's pinned `store.plan_changed` is unchanged.

`packages.shared_number` (1 = the package includes the shared platform number, default 1): the shared-number join needs an active or trialing plan whose package has it (`docs/shared-number.md`). Nothing in billing changes for a package that has it.

## Packages: three writers, one place (`PACKAGE_CHECKOUT_ENABLED` for purchase)
A workspace's package is D1 `workspace_subscriptions`, written ONLY in `src/core/billing/subscriptions.ts` (`setSubscription`, `cancelSubscription`, `rollRenewals`). Each write is one D1 batch: the row is upserted with `version = version + 1` in the same statement (racing writers never share or lower a version), `source` (`store_plan` | `operator` | `purchase`) is recorded, and a `billing_audit` row (`subscription_set`, ref = event id / operator user id / order id) is appended only if the row changed. Only after the batch commits does `announceSubscription` push `applyEntitlement` to the workspace and queue `whatsapp.entitlement_changed {packageId, automation, status, validUntil, version}` (event id = f(workspace, version): announcing again is harmless). A failed push is healed by the daily reconcile; a failed Store queue is logged (`entitlement_event_not_queued`) and never undoes the write.
Rules live in SQL, never read-then-write: the SAME package written again while it runs keeps `period_start` (its AI credits are neither refilled nor expired; only the end moves); a different package, or one that has ended, starts a new period now. Package AI credits are valid for their period only and never carry over.
1. **Store plan** (`store.plan_changed`, `billing/store-plan.ts`, in the queue consumer): the event is first CLAIMED in `store_plan_applied` (not older than the last applied `effectiveAt`, not the last event id) inside the same batch as the write, so replays and out-of-order events write nothing. `includesWhatsApp=true` -> package `store-included` (price 0, 100 AI credits, seeded by migration 0008) with the event's `status`/`periodEnd`, else active until `effectiveAt` + 31 days. `false` -> cancels it. A running purchased or operator package is never replaced or cancelled by the Store plan (checked in the write's SQL). The marker also remembers what the Store plan says, so when a bought/operator package ends, the daily reconcile (and a refund) hands the store back to `store-included`.
2. **Operator**: `PUT /api/v1/operator/workspaces/:id/subscription {packageId, status, periodEnd, reason}` (super admin, session re-check fails closed, 404 for an unknown workspace/package, audited, immediate). Extending the same package keeps its period and credits; a different package starts a new period. Rows that existed before migration 0008 are operator-owned.
3. **Purchase** (owner): `GET /stores/:storeId/packages`, `POST /stores/:storeId/packages/:packageId/checkout` (no body needed; the amount is `packages.price_minor`, never from the client; session not revoked, fail closed; the checkout URL must be on the Kashier checkout origin) writes a pending `package_orders` row; `GET /stores/:storeId/packages/orders/:orderId` only reads and says `paid` only once the package was granted. Every route is 404 while the switch is off. The existing `POST /kashier/webhook` dispatches on the order id. A SUCCESS with the stored amount/currency runs ONE batch: claim (pending|failed|expired -> paid, `provider_ref` unique), subscription write only if the claim holds and `granted_at IS NULL`, stamp `granted_at`. Either all of it commits or none does; a retry after a lost response only re-announces. A second SUCCESS with another transaction id on a paid order grants nothing, alerts `package_duplicate_payment` and is recorded in `billing_audit`. Amount mismatch -> `package_amount_mismatch`, no grant. No card fee is added to a package. A payment that arrives after the order expired is still granted.
4. **Renewal is manual, and an early renewal queues**: the package runs its month. Buying the SAME package while it runs does not touch the running period or its credits: one `queued_periods` is added (one payment = one extra period). Each order records what it paid for: `owns_running` (the order that owns the running period) or `queued_seq` (its place in the queue); an order with neither paid for a period that has ended. At the old `period_end` the workspace's `subscription_expire` task asks the control plane to roll the queue (`rollRenewals`): the new period starts at the old end with a fresh grant, the unused old credits expire. The daily reconcile rolls any that were missed. Buying a DIFFERENT package replaces the running one now (new period, upgrade rule above). 7 days before the end the inbox banner shows a renew line (not for `store-included`).
5. **Provider refund / chargeback** of a package order (the refund is its own transaction; each is applied once, keyed by its transaction id in `package_refunds`):
   - **Full** (cumulative refunds reach the order amount; alert `package_refunded` / `package_chargeback`): the order becomes `refunded` / `charged_back`. If it owns the running period and nothing is queued, the plan is `cancelled` with `period_end = now` and a higher version (pushed, announced to the Store), the unused part of that period's grant is zeroed with a ledger `expire:refund:<orderId>` row (used credits stay used, purchased credits are never touched, every expiry is counted against the period's grant so a partial refund followed by a full refund, a period end or another partial refund never expires the same credits twice; nothing is deleted; if that step fails the webhook answers 5xx and the retry does it, once), and a store whose Store plan includes WhatsApp falls back to `store-included`. If it owns the running period and a period is queued, the running one ends now and the next queued period starts immediately (fresh grant). If it paid for a queued period, only that period is removed and later ones move up. If its period already ended, the plan is untouched.
   - **Partial** (alert `package_partial_refund`): the running period it owns is shortened by the refunded fraction (`new_end = max(now, period_start + (period_end - period_start) x (remaining - refunded) / remaining)`, where `remaining` is the order amount not yet refunded), the version goes up and the Store is told, and the same fraction of the period's unused credits expires (`expire:partial:<refundTx>`; the fraction is stored with the refund when it is decided and reused on retry). The full-or-partial decision is made inside the batch: the refund row is written only if the order still has the refunded total it was decided on, so two concurrent halves end as one full refund. A partial refund of a period that has not started changes no period (recorded in `refunded_minor` only).
6. **Daily** (`repairPackageOrders`): a `paid` order with `granted_at` NULL (should be impossible) is granted and alerted `package_paid_not_granted`; pending orders older than 24 h become `expired`.

## Top-ups (7.4), `TOPUPS_ENABLED=true`
`POST /wallet/topups {amountMinor}` (owner, session not revoked via the `ACCOUNTS` binding `isRevoked(sid)`; unbound -> 503) writes a pending D1 `topups` row and returns the hosted checkout URL. The merchant pays the card fee ON TOP (`KASHIER_FEE_BPS`, `KASHIER_FEE_FIXED_MINOR`); the wallet is credited the exact amount (WA-TOPUP-FEE-1). `POST /kashier/webhook`: HMAC-SHA256 (hex, constant-time) over exactly the fields named in `data.signatureKeys` (sorted, `key=encodeURIComponent(value)` joined by `&`; we require amount, currency, merchantOrderId, status and transactionId to be among them) (https://developers.kashier.io/docs/webhooks). **The top-level `event` label (`pay` / `refund` / `partial_refund` / `reversal`) is NOT signed, so it is never applied.** For an order of ours, before any money or entitlement effect, we ask Kashier for ITS record of the signed transaction id (`GET {KASHIER_API_URL}/v2/aggregator/transactions/:id`, `Authorization: <KASHIER_SECRET_KEY>`) and act on the kind (payment / refund / chargeback) and status Kashier reports; the signed amount, currency, order id and transaction id are kept. If Kashier cannot be reached, answers 404 (not there yet), reports another transaction/order/status or an unknown operation, the transaction id is not a plain `[A-Za-z0-9_-]{1,64}` id, `KASHIER_API_URL` is not https, or the secret key is not configured, the webhook answers 503 and nothing happens. The delivery is kept in `unconfirmed_webhooks` (only what re-verification needs: the fields named in `signatureKeys`, the signature and our order id) and the daily pass (`reconfirmUnconfirmed`) runs it through the same path as a live webhook, so the claim on the transaction id makes it one effect whichever confirms first. One attempt a day; every terminal outcome (credited, granted, failed, amount_mismatch, refund_refused, refunded, duplicate_success, ...) closes the row with that `resolution`; one still open after 24 h raises `webhook_unconfirmed_aged` once, and after 14 attempts it is `abandoned` with `webhook_unconfirmed_abandoned` once (the structured alert line the alert bridge turns into a notice, like every other money alert) and is no longer retried. Only open, due rows are read, so closed or abandoned rows never take a slot. A refund that is confirmed BEFORE its payment is credited or granted is kept open (`payment_pending`) and run again the moment the payment is credited, by whichever path credits it, so the two net out. A package refund that loses six races in a row answers 5xx and is kept (`refund_contention`) for the daily pass. Closed rows are deleted 30 days after they close. Checkout (top-ups and packages) refuses with 503 `unavailable` while the secret key is missing. Idempotency keys bind signed values only (`kashier:<transactionId>:<status>`). On top of that: a payment is accepted only if the order has no transaction yet or this one (a second, different success alerts `duplicate_success` and does nothing); a refund is accepted only if its transaction id differs from the payment's and the top-up is `paid` (a package order: `paid`) (else `refund_refused`). NOT verified live: the operation value of a refund in the details API and whether a transaction is queryable the instant its webhook arrives. SUCCESS + order id + amount + currency must match OUR row; the workspace comes from the row; credit ref `kashier:<transactionId>`; debt is settled first by arithmetic. The browser return (`GET /wallet/topups/:orderId`) only reads. Provider refund/chargeback -> negative `chargeback` row + alert. Secrets: `KASHIER_API_KEY` (Payment API Key: checkout hash + webhook HMAC), `KASHIER_SECRET_KEY` (a DIFFERENT key, the Kashier Secret key: authenticates the transaction-details confirmation), `KASHIER_MERCHANT_ID`; var `KASHIER_API_URL` (default `https://api.kashier.io`, test `https://test-api.kashier.io`). **Inquiry (daily repair of a lost webhook)**: `repairTopups` (pending top-ups older than 15 min, expired after 7 days) and `repairPackageOrders` (pending or expired package orders 15 min to 7 days old, only while `PACKAGE_CHECKOUT_ENABLED`) ask `PaymentProvider.inquire(orderId)`. Kashier's documented list call finds the payment by OUR order id (`GET {KASHIER_API_URL}/v2/aggregator/transactions?search=<orderId>&type=payment&limit=20`, `Authorization: <KASHIER_SECRET_KEY>`; https://developers.kashier.io/openapi.yaml `listTransactions`); only rows whose `merchantOrderId` equals our id are candidates and every one is confirmed with the SAME transaction-details call as the webhook (status, kind and order come from that record). A confirmed payment is applied through the webhook's own apply path (`applyTopupWebhook` / `applyPackageWebhook`: claim on the transaction id, amount and currency must match, so a repair racing the webhook, or running twice, is one credit or one grant). Kashier unreachable, an unclear answer, or several successful payments for one order (alert `inquiry_multiple_success`) change nothing and the order is asked again the next day; a wrong amount alerts (`topup_amount_mismatch` / `package_amount_mismatch`) and changes nothing; no payment found yet is simply pending. NOT verified live: the list row's amount field (`amount` or `totalAuthorizedAmount`), the checkout link and the refund call (see Refunds below).

## Card refunds and the refund webhook (`KASHIER_REFUNDS_ENABLED`, default off)
The wallet is debited ONCE per refund, at approval (`refund:<requestId>:<n>`). Everything Kashier reports afterwards about that money must be matched to it, never booked again. D1 `card_refunds` (migration 0010) has one row per refund transaction we know of, in WALLET units (`topups.amount_minor`; the card fee was never in the wallet and is never debited or refunded from it), written BEFORE Kashier is asked.
- **Off (default)**: Kashier's refund API is never called; every card chunk is a manual payout (bank / InstaPay), exactly as before.
- **On**: for each card top-up chunk (oldest first) a `card_refunds` row (`sending`) is written, then Kashier is asked once: `PUT {KASHIER_API_URL}/v3/payment/refund/{kashier order id}` `{apiOperation: "REFUND", reason: "refund-request:<id>:<n>", transaction: {amount}}` with `Authorization: <KASHIER_SECRET_KEY>` (https://developers.kashier.io/openapi.yaml `refundOrder`; the same operation as `PUT fep.kashier.io/v3/orders/{id}`, one hop closer, on the host we already allow-list). Kashier's order id is read from the paid transaction's details (`body.order.orderId`); without it nothing is sent and the chunk is manual. The row keeps the refund's own transaction id.
  - A clean `SUCCESS` (top-level status, `response.status`, operation `refund`, our amount, a plain transaction id) marks it refunded and adds to `topups.refunded_minor` in the same batch. `PENDING` stays `pending`. A clear refusal (4xx, FAILURE) or nothing sent (`unsupported` / `unavailable`) makes that chunk a manual payout.
  - Anything that might mean "processed" (timeout, 5xx, unreadable answer, another amount) is `uncertain`: the request stays `processing`, the call is NEVER repeated (Kashier documents no idempotency key; the request id is in `reason` for the operator), and a webhook, the refund status by id or the refund list settles it (`reconcileCardRefunds`, daily). Open for 3 days: alert `card_refund_stuck` once for a person to check Kashier's dashboard.
  - The request's split is derived from its rows (card = succeeded + linked, open = waiting, manual = the rest); `processing` while anything is open.
- **Refund webhook** (`topups.ts` -> `applyProviderRefund`): (1) the refund's id belongs to a row of ours and Kashier's own record says it is a card refund (`refund` / `partial_refund`) -> reconcile the row, no wallet movement (a chargeback / reversal / void carrying that id settles nothing and alerts `refund_id_conflict` P1); (2) else, for a real card refund only, an open API row of the same top-up with the same amount that has NO provider id yet -> bind the id, reconcile, no movement; (3) else a refund or chargeback we did not start -> ONE debit `chargeback:<refundId>` (replays post nothing) of its FULL amount in wallet units up to what the top-up credited (`amount_minor`; the card fee was never in the wallet and is never debited), the wallet may go into debt, and nothing already used by other refunds or open card refunds shrinks it. Beyond the credited amount, the card fee explains up to `fee_minor`; anything past that is recorded (`card_refunds.note`, `billing_audit` `refund_excess_review`) and raised as a P1 alert `refund_excess_for_review` for an operator, never dropped silently. A `FAILURE` webhook for our pending row makes it a manual payout.
- **Refunded in Kashier's dashboard** (a manual payout paid by refunding the card there): the operator links it, `POST /api/v1/operator/refund-requests/:id/link-dashboard-refund {kashierRefundId, amountMinor, orderId?}` (field in the operator refund queue). The link first asks Kashier (`type=refund` list + details): the id must be a `refund` / `partial_refund` for this top-up's order, SUCCESS, for exactly that amount, else `refund_not_verified` (503 `provider_unavailable` if Kashier cannot be asked); nothing is recorded on a refusal. The link itself moves no money. If the refund's webhook already arrived first and debited a second time, giving that debit back is a wallet credit and goes through the adjustment flow (`requestAdjustment`) with a SECOND approver at ANY amount (money moved from a manual action): a different super admin must approve; the requester cannot approve their own. The adjustment has the deterministic id `relink:<refund id>`.
- **Debit phase first**: an approval posts ALL its wallet debits (and writes every card refund row) before any provider call. If that phase aborts (the balance shrank), no provider call was made, the request stays `processing` with no manual amount (money that was never debited is never offered for payout) and alert `refund_debit_incomplete` (P1) asks a person to look. Only when the phase is complete (`refund_requests.debit_complete`) can the request become `manual_payout` or `paid`. The approval's PLAN (`refund_chunks`: amounts, refs, top-ups, transactions) is recorded once before any money moves; a resume of an aborted run replays that plan, never recomputing it from today's totals. One run at a time: the approval claims the request with a lease (`claimed_by`, `lease_until`, 5 min, compare-and-swap) and each card refund row is flipped `sending` -> `calling` by a guarded UPDATE before the provider is asked, so two runs (or two resumes) can never send the same row twice. The card refund rows of the whole plan are written in the SAME batch as the plan as `planned` (a reservation only: counted by every room sum together with `held` refunds, but invisible to the webhook matcher, the reconciler and mark-failed until the row's wallet chunk is posted and it flips to `sending`), so any other approval's planning sees them at once, and right before each provider call the guarded flip re-checks that the top-up still has room (`amount_minor - refunded_minor` minus the other open rows ahead of this one: already calling/pending/uncertain, or planned earlier); a row that no longer fits is NOT sent: it is failed by ONE atomic statement (re-checking it is still `sending` and still has no room, so a row another run just moved to `calling` is never failed), becomes a manual payout and raises `card_refund_over_refundable` (P1). Only an approval can resume; a **reject** only closes a request nobody has started (`pending`): abandoning a partly debited request is a separate operator flow that must first reverse the posted `refund:<id>:*` entries.
- **Id mismatch trap (`refund_held`)**: our API refund is recorded with the id Kashier answered with (R). If Kashier's webhook names it with another id (W), a real card refund of the same top-up and amount, created within 7 days, whose refund (R) no webhook has confirmed yet, is HELD instead of debited: a `held` row, alert `refund_held` (P1, once per W), no wallet movement. An operator matches it (`POST /api/v1/operator/card-refunds/held/:refundId/match`): the candidate refund (`card_refunds.candidate_id`) must exist, be unconfirmed, in succeeded / pending / linked, on the same order and amount, and the guarded batch must change exactly that one row, else `not_verified` and nothing changes; Kashier must list W as a successful card refund for that order and amount; if Kashier lists BOTH W and the candidate's own id as separate successful refunds, money left twice: the match is refused (`separate_refund_debited`) and W is debited as an unknown refund (P1 `refund_held_debited`). A match marks our refund confirmed and moves no money. A chargeback or reversal is never held: it debits in full. **Verify R == W on the first live refund before enabling `KASHIER_REFUNDS_ENABLED`.**
- **A refund left `sending`/`uncertain`** (a crash, a lost answer): the operator can turn it into a manual payout (`POST /api/v1/operator/refund-requests/:id/card-refunds/:cardRefundId/mark-failed`) only after Kashier's refund list shows no successful refund of that amount for the top-up that another row has not claimed.
- **What stays on with `KASHIER_REFUNDS_ENABLED` off**: the double-debit fix is always on (it corrects a bug that predates the switch): the refund webhook is matched against recorded refunds and a refund or chargeback we did not start is debited once, its full amount up to what the top-up credited, with the excess and a refund that finds nothing credited raised as P1 review items (`refund_excess_for_review`, `refund_unmatched_no_credit`; the delivery is answered 200, never retried forever). The dashboard-refund link and the held-refund match are operator tools and need only the Kashier credentials. What the switch controls is exactly one thing: whether approving a refund asks Kashier to refund the card (off = every card chunk is a manual payout and no `card_refunds` row of source `api` is written).
- **The Kashier API origin is pinned**: `KASHIER_API_URL` must be https on `kashier.io` or a subdomain (`api.`, `test-api.`); any other value makes every call (inquiry, confirmation, refund) refuse before a request is made, so the secret key is never sent elsewhere.
- NOT VERIFIED live: Kashier's refund response shape, that the dashboard-host route accepts the order id from the details, PENDING behaviour, the refund webhook payload (the docs list the event names only) and that refund rows carry the original merchant order id. Check the first real refund (`docs/launch/README.md`).

## InstaPay billing (`INSTAPAY_BILLING_ENABLED`, default off)
The launch payment method for packages AND wallet top-ups until Kashier is approved; Kashier stays behind its own switches. Copies the behaviour of Ebda Store's "pay with InstaPay" flow (transfer, reference, proof, a human confirms).
- **Merchant (owner only, session revocation-checked like top-ups; staff get 403)**, `GET|POST /api/v1/stores/:storeId/wallet/instapay`, `PUT .../wallet/instapay/:requestId/proof`. `POST {kind: 'package', packageId}` or `{kind: 'topup', amountMinor}` (strict body; **the amount is computed on the server**: `packages.price_minor`, or the top-up amount within the card top-up min/max; at most 5 open requests). The answer carries the payee (`handle`, `name`, optional `qrUrl`), the exact amount, a unique human-typable `reference` (`WA-` + 8 characters without 0/O/1/I) and an expiry 48 h ahead. Payee details come from the brand pack (`instapayPayee`: the Ebda pack maps `EBDA_INSTAPAY_HANDLE` secret, `EBDA_INSTAPAY_QR_URL` and `EBDA_INSTAPAY_PAYEE_NAME`, the same values `ebda-api` uses, so `src/core` never names them); a brand without them gets no InstaPay billing (503, fail closed), never an empty address.
- **The proof**: jpeg / png / webp / pdf, at most 5 MB, checked by size and by magic bytes (the bytes decide, a lying content type or SVG/HTML is 415, over 5 MB is 413), stored PRIVATE in R2 under `instapay-proof/<workspace>/<request>.<ext>` (no public route and the media routes do not know the key). A proof uploaded after the 48 h expiry is refused. States: `awaiting_proof` -> `under_review` -> `confirmed` | `rejected` (with the operator's reason, shown to the merchant in the Wallet screen), or `expired`.
- **Operator (super admin, writes re-check the session, audited in `billing_audit`)**, `GET /api/v1/operator/instapay?state=`, `GET .../instapay/:id/proof-link` (a link signed with HMAC that works for 2 minutes and names one request; opening it is audited), `POST .../instapay/:id/confirm`, `POST .../instapay/:id/reject {reason}`. **Maker-checker**: the person who made the request never confirms or rejects it; at or above `ADJUSTMENT_APPROVAL_MINOR` a second, different operator must confirm (the first records `first_approver`). Every transition is one conditional UPDATE, so confirm, reject, expiry and upload racing each other end in one outcome.
- **Effects, exactly once, through the card payment's own paths**: the request writes its order in the same batch (a `package_orders` row or a `topups` row with `provider = 'instapay'`, no card fee). Confirmation runs `grantOrder` (-> `setSubscription` + the `whatsapp.entitlement_changed` event, ref `instapay:<reference>`) or the top-up credit (wallet post with the ledger outbox, ref `instapay:<reference>`); the unique reference, the claim on the order and the idempotent ref make a double confirm, a retry or the daily `repairInstapay` (a confirmed request whose grant did not finish, alert `instapay_confirmed_not_granted`) grant once. A request whose amount no longer matches its order is refused (`instapay_amount_mismatch`, P1). The Kashier repair and expiry passes ignore `provider = 'instapay'` orders; an InstaPay top-up has no card, so a refund of its share is a manual payout.
- **Daily**: `expireInstapay` (no proof in 48 h), `repairInstapay`, `overdueInstapay`.
- **Review SLA**: 4 business hours (Sunday to Thursday, 09:00-17:00 Africa/Cairo, computed with Intl so daylight saving is right). The operator console shows it; a proof pending longer raises `instapay_proof_overdue` (severity P1) once. Rejection is in-app only (the Wallet screen shows the reason): no suitable utility WhatsApp template exists yet.
- Alerts: `instapay_proof_overdue`, `instapay_confirmed_not_granted`, `instapay_grant_failed`, `instapay_amount_mismatch`, `instapay_repair_failed`, `instapay_expiry_failed`, `instapay_overdue_check_failed`.

## Merchant API (under `/api/v1/stores/:storeId`)
`GET /wallet`, `GET /wallet/statement?month=YYYY-MM[&format=csv]` (owner/operator; the CSV defuses free-text cells that start with `= + - @` with a leading quote, but amounts such as `-0.80` stay plain numbers), `GET /wallet/estimate?category=&count=&country=`, `POST /wallet/topups`, `GET /wallet/topups/:orderId`, `GET /packages`, `POST /packages/:packageId/checkout`, `GET /packages/orders/:orderId` (switch `PACKAGE_CHECKOUT_ENABLED`), `GET|POST /wallet/refund-requests` (owner; WA-REFUND-1 rules: plan period over, <= 12 months, >= 50 EGP, <= the positive available balance, debt first).

## Operator API (`/api/v1/operator/*`, super admin only)
Every non-GET call re-checks the session with the accounts service (`isRevoked`) and fails closed (403 revoked, 503 binding missing/erroring).
Pricing settings (`GET|POST /pricing-settings`; new version >= 1 h ahead, reason required, audited old -> new), `GET|POST /pricing-overrides/:workspaceId`, `GET|POST /rate-cards` and `/fx-rates` (>= 24 h ahead), `PUT /numbers/:phoneNumberId/funding`, `GET /refund-requests`, `POST /refund-requests/:id/decision` (approve debits the wallet, then with `KASHIER_REFUNDS_ENABLED` refunds the card FIFO through Kashier, the rest is a manual bank/InstaPay payout), `/link-dashboard-refund` and `/manual-paid`, `POST /workspaces/:id/adjustments` + `POST /adjustments/:id/decision` (the threshold `ADJUSTMENT_APPROVAL_MINOR` is cumulative per operator over a rolling 24 h, absolute values, all workspaces, plus `ADJUSTMENT_DAILY_CAP` self-approvals a day; beyond it a DIFFERENT super admin approves), `POST /trueups`, `GET /workspaces/:id/wallet`, `PUT /workspaces/:id/subscription`, `GET /change-log`.

## Month close (WA-SHARED-FREE-1)
Each workspace's `shared_number_trueup` task reports its service charges per platform number to `shared_number_usage`; the operator enters what Meta actually billed (`POST /trueups`, once per month+number); the task then credits the workspace its pro-rata share of `max(0, charged - actual)` as one `meta_adjust` `trueup:<yyyy-mm>:<workspace>`. Meta's own pricing analytics are not pulled automatically (operator-fed).

## Switches and secrets
`TOPUPS_ENABLED` (default off), `INSTAPAY_BILLING_ENABLED` (default off; InstaPay billing, see above; needs the brand's payee settings), `KASHIER_REFUNDS_ENABLED` (default off; card refunds through Kashier, see above), `PACKAGE_CHECKOUT_ENABLED` (default off; needs the same Kashier settings and `ACCOUNTS`; the Kashier webhook answers 404 only when both switches are off), `KASHIER_MERCHANT_ID`, `KASHIER_API_KEY`, `KASHIER_SECRET_KEY` (required: without it every money webhook answers 503), `KASHIER_API_URL`, `KASHIER_CHECKOUT_URL`, `KASHIER_FEE_BPS`, `KASHIER_FEE_FIXED_MINOR`, `ACCOUNTS` (service binding), `ADJUSTMENT_APPROVAL_MINOR`, `ADJUSTMENT_DAILY_CAP`. Launch defaults in D1: margin 0%, overdraft 50 EGP, VAT 0 (Q5 open), no rate cards and no FX (publish both before a platform number sends).

## In the page (web)
- **Wallet** (rail "المحفظة", every role can read): balance / held / available / AI credits, the 50 EGP overdraft in one sentence, debt (paid first by the next top-up), who pays Meta per active number (`merchant_card` gets the "WhatsApp bills your card directly" notice; `GET /wallet` reports a number with no funding row as `unknown`, shown as "not ready yet", never as a card payer), plan card (`past_due` says marketing is paused). Owner: a **Packages** card (hidden when the server answers 404; buy -> https checkout only; the pending order `wallet.pendingPackage` is polled via `GET /packages/orders/:id`, and "activated" shows only when the order is `paid`). Owner only: top-up (shown only when `topupsEnabled`; the card fee is on top, the wallet gets the exact amount; the order is created first so the fee is shown before redirecting; only an `https` checkout URL is ever opened), statement by month (not for staff) with a token-fetched CSV, refund request (minimum 50 EGP, rules in one sentence, past requests with state and the reviewer's note).
- **Top-up never claims success from the redirect.** The pending order (`wallet.pendingTopup` in localStorage, 3 h) survives the round trip; on focus and every 8 s the page re-reads the wallet and `GET /wallet/topups/:orderId`. "Arrived" shows when the order is `paid` (the server credits before it marks paid); the balance growing by the amount counts only when the order itself cannot be asked (a refund or adjustment also moves the balance); `failed`/`expired` says nothing was taken.
- **Inbox banner**: a bought package ending within 7 days shows a renew line (not `store-included`); `lowBalance` or debt shows a calm banner above the conversation list with a link to the wallet. "Marketing paused" is said only when available <= 0 AND at least one active number is `platform_line` (with cards paying Meta the wallet does not gate campaigns).
- **Campaign review**: a zero per-message cost reads "WhatsApp bills your card directly" only when every active number is `merchant_card`; otherwise it stays "price not ready".
- **Operator** ("لوحة التشغيل", rail item only for `super_admin`; the server still checks every call): pricing settings (current / scheduled / earlier; publish with percent and EGP parsed as exact integers, effective-from >= 1 h, reason >= 5 chars, "never retroactive"), rate cards (textarea `country,category,usd`, parsed client-side with line-numbered errors, >= 24 h) and FX, per-account margin override / who-pays-Meta / adjustment request, refund queue (approve explains the wallet is debited first and asks to confirm), adjustments (your own pending request has no approve/reject and says another super admin must decide), change log. A `503` on any write shows "session protection is not switched on yet, changes are locked"; reads keep working.
