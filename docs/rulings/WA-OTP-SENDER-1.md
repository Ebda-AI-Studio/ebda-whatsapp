# Ruling WA-OTP-SENDER-1

**Decision:** a sign-in code for a platform account (Ebda accounts, today: password reset) is sent ONLY from the Ebda AI Studio platform number, through the `PlatformOtp.sendCode(phone, code)` entrypoint (no store id). It is never sent through a store's number. `PlatformOtp` touches no workspace: no Durable Object call, conversation, contact, message, search row, realtime event, export, backup or AI context; the code exists only in the Graph request. It answers `disabled` (sends nothing) until `PLATFORM_OTP_PHONE_NUMBER_ID` and `PLATFORM_OTP_TEMPLATE` (an approved AUTHENTICATION template on that WABA) are both set; the platform number is a Meta, third-party step that has not happened.

**Why:** the security review (2026-10-29) found that the accounts caller sent the owner's code through each owned store's number (`WhatsAppOtp.sendOtp(storeId, ...)`). A message sent from a store's number is a row in that store's inbox history, visible to every staff member of the store, which makes it an account-takeover path.

**Evidence:** `test/platform-otp.test.ts` - off until configured; sent from the platform number id; bad input and other countries refused before any Graph call; after a send, two seeded stores' databases and every D1 table hold neither the code nor the number, and no log line does.

**Sweep (whole class, 2026-10-29):** every path in both repos that sends a code or link through a WhatsApp number: (1) `WhatsAppOtp.sendOtp` / `queueOtp` (`src/core/otp.ts`, `workspace-do.ts`) is the Store-link customer OTP (OTP-1: a STORE's own customer signing in to that store, sent from that store's number on purpose). It stores the message with the text masked (`OTP_MASK`), so staff see a template send without the code, but the row exists and the code is in the Graph request; it is not used for accounts any more. The Store (`apps/api`, `apps/web`) has no caller of it, so it is off; any future caller must be a store-customer flow, never an account flow. (2) Store-order proof links (`PROOF_URL_SECRET`) are signed links for the Store to fetch a payment screenshot, not sign-in material. (3) No magic-link sender exists in either repo. Found: 1 path of the class (the accounts caller), fixed in ebda-store.

**Residual:** per-phone throttling for platform codes lives in accounts (3 resets per address per window, IP caps); this Worker keeps no per-phone state for them, because that state would be one more place holding phone numbers. Cost if wrong: before the platform number exists nothing is sent; once it does, a caller bug that skipped accounts' throttle could send many codes at our cost to Egyptian numbers (country allow-list stays on) - add a D1 counter then.

**Cost if wrong (decision):** a platform number that is delayed means no WhatsApp channel for accounts (email only, as today); using a store number instead would reopen the takeover path.
