# Ruling CHAT-ASSIST-1

**Decision:** Two owner-assistant tools reach the Store over the bridge, authorised THERE by the calling person's live role (never a claim in our token). `store_top_products` (free read; owner and staff) answers best sellers of today / 7d / 30d (default 30d, top 1-10) with the Store's own analytics, in minor units; the tool prints revenue as two-decimal strings and the invented-figure guard (`routes/assistant-observe.ts`) treats "5,400" and "5400" as the same figure. `store_create_coupon` (confirm class, money, irreversible, owner only) creates a percentage (1-90) or fixed (at most 50,000) coupon, window 1-90 days (`durationDays` from the confirm press, or `startsAt`/`endsAt`), optional usage limit and code, through `CouponService.create` on the Store. Chat holds no coupon logic beyond the same limits, checked early so a card never promises what the Store refuses. Orders-count and sales-total questions stay a no-tool reply (`NO_STORE_METRICS`); a best-sellers question is no longer one (`isTopSellersQuestion`).

**Evidence:** Store ruling CHAT-ASSIST-1 (`owner-tools.ts`, `tests/unit/wa-bridge/wa-bridge-owner-tools.test.ts`); `test/smart-layer/store-tools.test.ts` (confirm-before-write, one coupon per preview, scope, validation, audit before/after, no invented numbers); routes `GET /store/top-products` (member) and `POST /store/coupons` (owner, never an operator session) are in the route-authz matrix, `person_only` for server tokens, and in capabilities `store.top-products` / `store.coupon-create`. Plan gate: none in Chat; in the Store `coupons` is in every plan baseline (free included), so only the merchant's own feature switch can refuse (`FEATURE_DISABLED`).

**Cost if wrong:** a wrong coupon discounts up to 90% for at most 90 days on one store and the owner switches it off in the Store admin (the assistant cannot delete one); a generated code is an HMAC (key derived from `TOKEN_ENC_KEY`, domain-separated) so it is not guessable; the engine re-runs `preview` at the press and compares it, so it cannot be random per call and identical terms on one day give one code; the code embeds the day, so a card held across midnight re-previews instead of creating a different code than it showed.
