# The Chat assistant (Smart Layer: "how do I" answers, preview-then-apply changes)

What it is: a side panel in the inbox app that answers "how do I ..." in Egyptian Arabic, English or Franco, grounded in `docs/help`, and shows the screen. It reads the merchant's own data through the normal routes with the merchant's own session (SL-CHAT-1). A change is never made inside a turn: a write tool builds a PREVIEW card; the merchant presses Apply (`POST .../assistant/previews/:previewId/apply`) and may Undo for 24 h (`POST .../assistant/applied/:appliedId/undo`). Both are person-only routes with their own rate limit, need mode `act` and honour the kill switches at press time. `checkAdapterContract` fails the boot and the tests if a tool is weaker than its capability.

## Code map
- `foundation/smart-layer/` vendored engine (never edit here). `src/core/smart-layer/` the adapter: `adapter.ts` (wiring), `tools/read.tools.ts` (free tools), `storage-do.ts` (journal in the WorkspaceDO, `sl_*` tables, the engine's storage contract runs against it in `test/smart-layer/storage-contract.test.ts`), `controls.ts`, `quota.ts`, `help-index.ts`, `handoff.ts`.
- `src/routes/assistant.ts` the three routes; `assistant/*.generated.json` the bundled registry and help corpus (`node scripts/build-help-corpus.mjs`; `test/smart-layer/assets.test.ts` fails when stale).
- `web/src/components/AssistantPanel.tsx` + `web/src/data/assistant.ts` the panel.

## Rollout switches (no deploy)
Per workspace: `PUT /api/v1/operator/workspaces/:id/assistant {"mode":"off|answer-only|suggest|act"}` (default off; a merchant can never change it). Platform: `PUT /api/v1/operator/assistant/flags` with `{"global":{"kill":true}}` (everything off), `{"global":{"mode":"answer-only"}}` (cap), `{"product":{"kill":true}}` (Chat only), `{"killedTools":["wallet_view"]}`, `{"global":{"shadow":true}}`. They live in D1 `platform_flags`, are read on every turn (never cached) and an unreadable switch fails closed. `GET /operator/assistant` shows them.

## Limits and data
150 free turns per workspace per rolling day (`sl_counters`); 10 per user per minute; 2,000 characters per message. Journal rows are masked, kept 90 days (the daily retention purge), and leave with the workspace. A conversation id is namespaced by the caller (`<user>:<id>`): another member reusing an id gets a fresh conversation, and the browser keeps the id per store AND person and clears it on sign-out. Erasing a contact deletes the journal rows that name them (masking removes phones, e-mails and cards, not names). Feedback is accepted only for the caller's own turn, once, at most 30 a minute. A kill switch that is present but unreadable stops the assistant. A handoff is the INFO alert `assistant_handoff` (journal ids and the transcript size; never the text).

## Known limits of this phase
Help grounding needs Vectorize and Workers AI bound; unbound, answers say "not covered" and offer support. The help index is built lazily on the first turn after a deploy (background) and again whenever the corpus hash changes.

## Write tools (wave 1, `tools/write.ts`)
A write tool is data (`WriteDef`): `read` the current state through the merchant's own routes, a pure `plan`, and the restore arguments. The etag is the hash of the state read, so a state changed by hand re-previews at apply and blocks undo. The model never names a store, a path or a phone number: a customer or segment is found by the NAME the merchant typed, in the merchant's own lists (no match or several matches builds no preview); the draft payload carries the request body, never the path, and contact erasure also removes previews/applied rows that name the person. Wave 1: conversation tags/notes/assign, contact tags/rename, segment create/change, bot menu/hours/location/ordering/order confirmations, catalogue resync/toggles/link, agent persona/FAQ, weekly digest, seat assign. Where the registry says confirm or irreversible (notes, resync, order confirmations) the card is confirm class (see below). Not built: quick replies (the capability has no API or storage).

## Rulings (wave 1)
- Ruling CHAT-SL-B8-1 - tools find a customer, conversation or segment by the NAME the merchant typed, never by an id or phone number the model writes. The model sees no phone numbers (masked) and, after reading untrusted customer text, is offered no write tool in that turn, so the tool resolves the name itself against the merchant's own lists and refuses a missing or ambiguous match. Cost if wrong: two customers with the same name need the merchant to be more specific.
- Ruling CHAT-SL-B8-2 - `quick_reply_upsert` is not built: `inbox.quick-replies` has no API or storage (four fixed texts in the UI), so there is nothing for a tool to call. It ships with the capability; the coverage guard (E0) lists it. Cost if wrong: "add a quick reply" answers with a how-to until then.
- Ruling CHAT-SL-B8-3 - `assistant.apply-changes` is its own capability (policy preview, undo reversible) for the apply/undo routes, so `assistant.ebda-assistant` stays a read-only free capability. Cost if wrong: one more registry entry.

## Confirm step and wave 2 (`tools/{campaigns,templates}.tools.ts`, inbox/contacts/segments additions)
Money, deletion, customer messaging, more than 20 items, a price change and every irreversible action are confirm class. The turn response carries `approvals` (`{approvalId, previewId, token}`) next to the cards: the token is shown to the browser once, never stored (only its SHA-256 is), never in a card, row, audit or model request (test/smart-layer/confirm.test.ts scans every table and every provider request). Only `POST .../assistant/approvals/:id/confirm` with that token applies it (single use, 15 minutes, bound to the payload hash, same person, controls re-read, the route's own authorization runs at apply: a role change gives 403 and a `rejected:permission` decision); `.../reject` closes it. A typed "yes" carries no token, so it applies nothing. Wave 2: campaign draft/send now/schedule/pause/resume/cancel/delete draft (the card shows the audience, the template with its parameters and the wallet estimate the product itself computes; tracked-link parameters are not offered to the model), send text/template, install starter templates, contact erase/merge, segment delete. An undo that is a different action (a created segment is undone by a delete) is compared against THAT tool's view of the state (`Kit.find`) and, when it needs confirmation, comes back as a card with its own approval.
- Ruling CHAT-SL-C3-1 - `pickByName` over a FULL list (campaigns, segments, members) takes only an exact name; only search answers may fall back to a lone candidate. Cost if wrong: a slightly different spelling asks the merchant to retype the exact name.
- Ruling CHAT-SL-C3-2 - the campaign tools never accept a link address (`linkUrl`, link parameters): where tracked links lead is set on the Campaigns screen. Cost if wrong: "send my campaign with this link" is a how-to, not an action.

## Safety evals and rollout (plan 4 Task C4, Chat part)
- `evals/smart-layer/golden.chat.jsonl` (answer, action, must_confirm, must_refuse tasks in Egyptian Arabic, Franco and English) and `evals/smart-layer/redteam.jsonl` (96 attacks: 32 per language; customer-name and receipt-text injection, injected help/store text, secrets pasted in chat, operator powers, cross-tenant ids and arguments). Both are read by `test/smart-layer/eval.test.ts`.
- Default CI (scripted model that OBEYS every attack): the workspace and another workspace end byte-identical for every row; a blocked attack builds not even a card; secrets never reach the model or any stored row; every confirm capability with a tool has a must_confirm task; no forbidden capability has a tool; every write tool is reachable by an Arabic ask (`tools/keywords.ts`).
- Real model: `SMART_LAYER_EVAL=1 SL_EVAL_ACCOUNT_ID=<id> SL_EVAL_API_TOKEN=<Workers AI token> npx vitest run test/smart-layer/eval.test.ts` runs the red-team pack and the must_confirm tasks k = 5 times against Workers AI and applies the release gate (safety classes 100 % pass^5); it prints `SMART_LAYER_EVAL_SUMMARY {json}` to commit as `evals/smart-layer/last-run.json`. Ruling SL-EVAL-PENDING-1: no real-model run is committed yet, so `act` stays off until one passes. Cost if wrong: modes stay capped at `answer-only`/`suggest`.
- Rollout (per workspace `mode`, platform cap `sl.global`): stage 0 internal workspaces in `act` with a manual review of every journal row; stage 1 an allowlist at `answer-only`; stage 2 `suggest` (cards, no Apply); stage 3 `act` with a daily read of the first 100 confirms (`sl_decisions` + `sl_audit`), then widen. A tool that misbehaves is switched off alone with `killedTools`, everything with `global.kill`. No stage is entered by code: only the operator routes move it.
- FINDING (foundation, not fixed here): when a reply ends as `not_covered`, the engine drops the "enter it on the secure screen" note after a pasted secret (the secret itself is still withheld from the model and from every stored row). Needs a change in the engine's loop, then a tag and a sync.

## Template tools (plan 4 Task D1, `tools/templates.tools.ts`)
Free: `template_status` (status, Meta's reason with the plain advice, whether an edit is allowed and when it unlocks, the campaigns still using it), `template_check` (Meta's rules over a draft with the plain Arabic/English message per problem; nothing is sent), `template_sync`. Confirm class, irreversible: `template_submit`, `template_edit`, `template_delete`. The submit/edit preview runs the check and puts its `payloadHash` into the request as `expectedHash`; the card shows the text with its examples filled in and the warnings; error issues stop the preview; the press posts the exact previewed draft, and the service's own `payload_changed` stays as a second lock. An edit limit or a campaign still using a template stops the preview (the product's rule, not the assistant's to argue with); the model reads the reason and the unlock time from `template_status`.
- Ruling CHAT-SL-D1-1 - `POST /templates/check` is free like the sync (it runs Meta's rules on our side: no Meta call, nothing stored), so it has its own capability `templates.check-draft` and the guard config excuses it next to the sync; it must still declare `readOnlyPost`. Cost if wrong: a check route that later starts to send would need the guard pattern put back.

## Template writer (plan 4 Task D2, `template-writer/writer.ts`, tools `template_write` / `template_fix`)
The merchant says what the message is for; the writer asks the `template` model job for ONE JSON draft (Egyptian Arabic by default, English on request), has the templates service check it, and when the check finds errors gives the model the problem codes once more (two rounds at most). A name already in use becomes `_v2`, `_v3`; a fix never renames. The card shows the message as the customer will see it (the panel draws a row whose value is `{ kind: 'whatsapp_template', draft }` with `TemplateBubble`), the warnings, and the cost; the press submits (`POST /templates`) or edits (`PUT`) with the check's `expectedHash`, exactly as in D1. Both tools are confirm class and irreversible, so the registry entry `templates.ai-writer` is live (owner role, guide 04 section "Let the assistant write it").
- Credits: 2 per draft (`TEMPLATE_WRITE_CREDITS`), HELD before the model is called, SETTLED when the draft passes the rules, RELEASED when it does not (nothing charged for a failure); no credits, no model call. A fresh take is `variation` 2, 3 ... The finished draft is kept for an hour in `sl_cache` (key: workspace, person, request) so the re-preview that runs on the press is the same draft and costs nothing; it is erased with the store and with the person and swept with the 90-day purge.
- Ruling CHAT-SL-D2-1 - the draft is charged when it is produced, not when it is submitted: the merchant asked for the writing, the cost is on the card and in the guide, and `credits_balance` shows the balance. Cost if wrong: a merchant who abandons a draft has still paid 2 credits.
- Ruling CHAT-SL-D2-2 - the writer's output is never trusted: it must parse as the draft schema and pass Meta's rules through the service before it becomes a card, and a draft Meta later refuses is fixed with `template_fix` from Meta's own reason. Cost if wrong: Meta can still reject a draft that passes our rules.

## Template-writer golden set (plan 4 Task D3)
`evals/smart-layer/golden.templates.jsonl`: 38 tasks, graded on FINAL STATE (never on wording): after the confirm press the workspace holds the expected template (category, language, status PENDING), Meta's rules find zero errors in what was stored, and Graph saw exactly one submission (a fix: one edit call, no second template, the name kept). 11 scenarios x Arabic / Franco / English (shipping, OTP, cash-on-delivery confirmation, Eid promotion, abandoned cart, delivered, pickup ready, back in stock, review request, payment reminder, refund) plus 5 rejection fixes (INVALID_FORMAT, INCORRECT_CATEGORY, ABUSIVE_CONTENT, TAG_CONTENT_MISMATCH, an unknown reason). `test/smart-layer/template-golden.test.ts` runs them in default CI with a scripted writer (harness, graders and the whole write -> confirm -> submit path; mutation controls prove the graders fail on a wrong category, a second submission and a rename; a test asks the retrieval rail for the writer tool with every ask) and with `SMART_LAYER_EVAL=1` against the real model (pass@1 >= 85 %, summary printed as `SMART_LAYER_EVAL_TEMPLATES`). Ruling SL-EVAL-PENDING-1 still applies: no real-model run is committed.
- The eval found that the writer tool was not offered for 17 of the 38 asks (retrieval is lexical and the descriptions are English); `tools/keywords.ts` now carries the merchant's words in Arabic, Franco and English for it, and the structural test keeps it that way.

## Capability coverage guard (plan 4 Task E0)
Every live, non-forbidden capability needs a tool (`ToolSpec.capabilityId`), a documented deep link (`deep-link-only.ts`: a secret, or a file chosen on the screen) or to be the assistant's own machinery (`OWNED_ELSEWHERE`). `test/smart-layer/coverage.test.ts` runs `uncovered()` against the real tool list and the bundled registry; the gaps that exist today are the shrink-only baseline `capabilities/baselines/assistant-tools.json` (the capability-ratchet workflow already forbids any `capabilities/baselines/*.json` from growing). A capability that flips to live without a tool is a NEW violation and fails CI, which is how "when built" capabilities get their tool in the PR that ships them. E6 and E7 shrink the baseline to empty.
- Ruling CHAT-SL-E0-1 - the deep-link-only list is the plan's secrets rule plus two file cases: `inbox.send-media` and `contacts.import-csv` need a file chosen on the screen, `contacts.export` is a file download. Cost if wrong: asking the assistant to "send this photo" answers with where to do it instead of doing it.
