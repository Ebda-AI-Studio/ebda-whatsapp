# Billing (Phase 7)

The UI (wallet, operator console) is built against the DTOs in `src/core/api/contract.ts` ("Billing (Phase 7)" block); see "In the page" at the end. Amounts are integer piasters (EGP x 100); the currency is always EGP.

## Who pays Meta (WA-FUND-1)
`number_funding(phone_number_id, funding)` in D1, copied into each workspace.
- `merchant_card`: Meta bills the merchant's card. The wallet is NEVER debited for these numbers; the message's Meta cost is recorded (`billable_sends.cost_usd_micros`) and shown on the statement (`cardCosts`).
- `platform_line` (the plan calls it the Ebda line; `src/core/**` may not name the brand): the wallet pays. Used for the shared number.
- **Funding must be KNOWN.** A number with no row is `unknown` and cannot send (`funding_unknown`: API 409, queued message failed with that reason, campaign paused `funding_unknown`, alert). Nothing stamps a default: the code path that creates a number writes it (`recordNumberFunding` / `fundingStatement` in `src/core/billing/funding.ts`): own-number connect (Phase 8.1) writes `merchant_card` in the same batch as the `phone_numbers` insert; the shared-number setup (8.2, `POST /api/v1/operator/shared-numbers`, `docs/shared-number.md`) writes `platform_line` in the same batch as the `shared_numbers` row; a member workspace's funding copy includes the platform number while it is an active member; the operator can change it (`PUT /api/v1/operator/numbers/:id/funding`, audited; the owning workspace's copy is refreshed in the same request, so the next send already follows it). A miss triggers an eager re-pull (at most every 10 s) before refusing.
- The wallet also pays for AI credits (separate ledger, below).

## Money flow for a platform_line message
1. **Price inputs** (D1, immutable effective-dated versions): `rate_cards(ver, effective_from, country, category, usd_micros)`, `fx_rates`, `pricing_settings` (margin, overdraft, FX buffer, VAT), `workspace_pricing_overrides` (margin per workspace). Each workspace copies them lazily (<= 30 min old; a workspace that never pulled decides nothing: claims defer 60 s, the API refuses). Rate cards/FX are published >= 24 h ahead, settings/overrides >= 1 h ahead, so the copy always has a version before it applies.
   - **VAT-0 (Ruling VAT-0, Ahmad 2026-10-26):** no VAT is charged: the provider is not VAT-registered and prices are final amounts. `vat_bps` stays 0: the operator route refuses anything else (`400 vat_locked`), the console shows it read-only, and a guard test checks no migration seeds it above 0. The VAT engine (`vatOf`, `vat_minor` on ledger rows) stays for a future registration, which needs a new ruling, a code change and the 30-day notice in terms 6.6 (the suite's VAT-0 clause, vendored at `vendor/legal/VAT-0-clause.md`, sha-pinned). Ruling WA-VAT0-1: the lock is in code, not a D1 trigger, so the VAT maths stays testable; cost if wrong: a direct D1 write could set VAT, but nothing in production writes pricing_settings outside this route.
2. **Pre-send** (at the API/Store-event queue for a refusal that writes nothing; at claim for everything): estimate = price by RECIPIENT market (calling code; unknown -> `ROW`) and category (a template's own category; a template with no known category is priced as `marketing`, the dearest, until Meta confirms it (WA-CATEGORY-1); everything else `service`) at the version in effect now. No price in effect -> refused `rate_unavailable` (never held at 0).
   - marketing: needs `available >= estimate` and no debt, else `wallet_empty` (a campaign pauses `wallet_empty`).
   - utility / service: may go down to `-credit_limit_minor` (default 50 EGP, WA-OVERDRAFT-1); beyond that they WAIT (<= 48 h, <= the 24 h window for free text): `wallet_wait` row, released FIFO when funds arrive, failed `wallet_empty_expired` at the deadline (fixed at the first wait).
   - authentication that cannot be paid fails at once (`wallet_empty`) so the Store falls back to e-mail.
   - `plan_blocked` (past_due / cancelled / expired, **or no entitlement row at all**: fail closed, a workspace the control plane has not pushed a plan to cannot send paid marketing) blocks marketing only; utility, authentication, service sends and inbox replies keep working. Evaluated by `marketingBlocked` (`src/core/billing/entitlements.ts`) at queueOutbound, queueTemplate, claim and campaign pages. Test workspaces get a version-0 baseline plan from the test helpers (`seedPlan`).
3. **Hold** `msg:<idempotencyKey>` (`wallet_holds`). `available = balance - held`. A campaign page reserves ONE parent hold `camp:<id>:p<n>`; its messages draw from it (no double reservation); the parent closes only when no message of the page is waiting.
4. **Meta statuses** carry `pricing {billable, pricing_model, category, type}`. `sent` + pricing re-estimates the hold to Meta's category. The FIRST `delivered`/`read` with a billable flag charges (`meta_charge`, ref `meta:<wamid>`, unique) at the rate/FX/settings version in effect at DELIVERY time. Not billable -> hold released. `failed` -> released. Non-PMP model -> `unpriced` alert, no charge. A later status naming another category posts the difference as `meta_adjust` (`adj:<wamid>:<category>`). No status within 31 days -> hold `expired` by the sweep; a late billable event still charges (the charge never needs a hold).
   - **No rate found at delivery** -> `pending_rate`: the hold STAYS; priced by the version in effect at delivery, else the earliest version after it, as soon as one arrives; after 7 days the held estimate is charged (alert). Never free.
   - WA-SHARED-FREE-1: service replies on a platform number are charged at the service rate whatever Meta's billable flag says; the `shared_number_trueup` task rebates the difference (below).
5. **Price**: `piasters = roundHalfEven(usd_micros x fx_micros x (10000 + margin_bps) x (10000 + fx_buffer_bps) / 10^18)` in BigInt, ONCE per row (the FX buffer adds to the plan's `/10^14` formula; with a zero buffer it is exactly that). VAT per row (`vat_bps`, 0 until Q5 is decided): `vat_minor = roundHalfEven(net x vat_bps / 10000)`. Statements sum stored rows; nothing is recomputed.

## Invariants (each has a test)
append-only ledger; `balance_after` chain; one charge per wamid under duplicate/out-of-order webhooks (incl. statuses before the accept); concurrent holds cannot exceed available; every terminal message path settles its hold (enqueue failure, opted-out drop, plan lapse, cancelled campaign, non-retryable failure, 131049 failure, rate-limited code, erasure, webhook failed, wait expiry, sweep); D1 mirror sum = DO sum after a drain; erasure leaves money intact; merchant_card numbers never debit; unknown funding / empty copy / missing rate never mean "free".

## Debt guard (WA-DEBT-1)
Charge at delivery, `meta_adjust` (category change, shared-number true-up) and chargebacks are external money facts: they are ALWAYS posted in full, so a wallet can sink past the overdraft limit. `debtGuard` (engine.ts, runs inside every `post`) sets the workspace's OWN debt flag `billing.debt_hold` once `balance < -2 x creditLimit` (`DEBT_SUSPEND_FACTOR`) and raises `wallet_debt_suspended` (P1). `isSuspended` reads three independent flags (operator `ops.suspended`, Store `store.hold`, debt `billing.debt_hold`), so every reason clears on its own: a posting that brings the balance back to `>= -creditLimit` clears only the debt flag; an operator unsuspend only the operator flag; a Store reactivation only the Store hold. The `wallet_debt_sync` task pauses running / scheduled campaigns with `wallet_empty` (queued pages parked, so no audience row fails; a top-up resumes nothing) and derives D1. **D1 `workspaces.suspended_*` is derived from the flags by one helper (`syncSuspendedMirror`, `ops/suspension-mirror.ts`) used by every writer**: reason = operator reason, else the Store tag, else `wallet_debt`; no flag = NULL. The operator suspend writes its audit row whenever the OPERATOR flag was not already on (a debt or Store hold in D1 does not make it a retry); offboarding's abuse hold is true only for an operator reason (`wallet_debt`, `store_*`, `offboarding` never hold an erasure). **The mirror only changes what it owns**: `syncSuspendedMirror` sets, replaces and clears a D1 row only when it is empty or holds `store_suspended` / `store_deleted` / `wallet_debt`; an operator reason (including one whose workspace half is missing after a `partial` suspend) and `offboarding` are never lifted or overwritten by a merchant-triggered sync; only the operator's explicit unsuspend (`operatorLift`) replaces an operator reason. **A debt survives erasure** (offboarding `suspend` step): the data erasure is never blocked, but a negative wallet is recorded once in the append-only offboarding log (`debt_preserved`, `debt_minor=N`), stays in the kept `ledger_mirror`, raises P1 `offboarding_debt_outstanding`, and is never written off (a write-off exists only for a positive balance, with explicit `acceptWriteOff`). Test: `test/billing-wallet-debt.test.ts`, `test/offboarding-review.test.ts`. Ruling: `docs/rulings/WA-DEBT-1.md`.

## Packages and entitlements (7.1)
`workspace_subscriptions(version)` in D1 -> `applyEntitlement` event (versions only move forward). Daily cron (`17 1 * * *`, the only cron) re-sends every subscription and repairs lost top-up webhooks. A new period grants `grant:<period_start>:<package>` AI credits and expires the last period's unused grant; an upgrade grants the difference. The Store's pinned `store.plan_changed` is unchanged.

`packages.shared_number` (1 = the package includes the shared platform number, default 1): the shared-number join needs an active or trialing plan whose package has it (`docs/shared-number.md`). Nothing in billing changes for a package that has it.

## No package, no service (WA-NOFREE-1) and the bounded grace (WA-GRACE-1)
There is no free plan. `store-included` (price 0) exists only while the Store plan says includesWhatsApp (written ONLY by the Store-plan path; the operator route refuses it, guard tests in `test/guards.test.ts` pin both this and "price_minor = 0 only for store-included" across D1 seeds). ONE function decides service: `serviceAllowed(sql, now)` in `entitlements.ts` = a plan IN EFFECT (WA-CANCEL-1: trialing / active / **cancelled**, each only while `period_end > now`, compared on EVERY check, so a workspace expires itself without waiting for the reconcile, an `expired` event or the alarm), or past_due inside `now < min(period_end, past_due_since + 7 days)`. No row, expired, or a plan whose period has ended = false; "cancelled" therefore means "cancelled AND the paid period has ended" (the Store sends `cancelled` while the period still runs and `expired` after; a refund cancels with `period_end = now`). One helper (`inEffect`) feeds `serviceAllowed`, `featureAllowed`, `memberLimit` and `marketingBlocked`, so `cancelled` in effect keeps its package features and does not block marketing by itself. The operator route refuses an active / trialing assignment with a past `periodEnd`. Background Workers AI spend (`kb_index`, `catalog_embed`, `scheduleCatalogEmbed`) stops without a package too (the nightly catalog chain survives). A message stuck in `claimed` past the stale window is failed `plan_required` at its next claim. Everything that sends or costs us asks it: the API send and upload (`403 plan_required`), `queueTemplate` / `queueFreeText` (OTP, order and COD confirmations, campaigns), the claim step (a queued message that meets a lapsed plan fails `plan_required` and settles its hold; an automatic reply is dropped), the inbound turn router (no bot, menu or AI agent), campaign paging (pauses `plan_blocked`), number connect / register and the shared-number join. Open: sign-in, reading, the package list, checkout (Kashier, InstaPay) and the wallet. Marketing keeps its own stricter gate (`marketingBlocked`: past_due blocks it at once). `past_due_since` is set in D1 (`0015_past_due_since.sql`) by `setSubscription` when the status first turns past_due (kept while it stays, cleared otherwise; the Store's `pastDueSince`, contract v1.4 / Store #218, is read defensively in `store-plan.ts` until re-vendored), travels on the entitlement event and is stored in the DO copy (DO migration v33). Meta costs are safe either way: an own number bills the merchant's card, the shared number spends the prepaid wallet, which fails closed. **A suspended or deleted Store store (STORE-STANDING-1, contract v1.6)** stops every spend on top of this, whatever package the workspace holds: the workspace's Store hold makes `isSuspended` true (send claim `workspace_suspended`, no bot / agent / front desk, no background Workers AI, campaigns paused `store_suspended`) until `store.reactivated`; see `store-link.md` and `docs/rulings/STORE-STANDING-1.md`.

## Yearly packages (P2, D1 0016 + DO migration v35 for `entitlements.period_months`)
`packages.period_months` is 1 or 12. `starter-yearly` 621000, `growth-yearly` 1341000, `pro-yearly` 3141000 (EGP minor, 9 x the monthly price) have the SAME limits and the SAME AI credits per MONTH as their monthly twin. Every package order records, when it is created and on the server only, `period_months` (the length it bought), `kind` and `from_package`; a purchase (Kashier or InstaPay, both through `planPurchase` and `grantOrder`) sets `period_end` = `period_start` + the ORDER's months (calendar months, UTC), so a queued 12-month period always rolls as 12 months of the package it was bought for, whatever the package row says later (`rollRenewals` takes the package and length from the order that becomes the owner). The entitlement event carries `periodMonths` (default 1) and the workspace stores it (`entitlements.period_months`).

**AI credits are granted monthly, never 12x upfront.** The event grants month 1 (`grant:<period_start>:<package>`); ONE `credit_month` task (a singleton row) then sits at the next monthly anniversary. `runCreditMonth` derives everything from the ledger and the entitlement, never from the clock or the payload: the next month is the one after the LAST month actually granted (`lastGrantStart`), so a missed run catches up one month at a time in order and a replayed event cannot skip a month; a duplicate row or a stale payload finds nothing ungranted and changes nothing. It expires the previous month's unused grant (purchased credits roll over), grants the new month under its own ref, and returns the next due time. A plan cancelled while in effect (WA-CANCEL-1) keeps earning its months until `period_end`; past_due and expired do not. A renewal or the period end expires the unused part of the LATEST month's grant. Monthly packages are untouched (one grant per period, no `credit_month` row). **Anniversaries are computed from the period start, not chained**: a period starting 31 January has its months begin on 31 Jan, 3 Mar (31 Jan + 1 month overflows), 31 Mar, 1 May, 31 May ...; each month index is still granted exactly once, and two anniversaries can fall in the same calendar month.

**WA-YEARLY-SWITCH-2 (supersedes SWITCH-1): changing package while a YEARLY period is running.** Decided by `planPurchase` on the server:
- *Upgrade* (a higher YEARLY package: its price/12 above the running one's): the merchant pays `(new price/12 - old price/12) x remaining months`, where the remaining months are the CURRENT month plus every whole month after it (in month 12: 1), rounded DOWN to a whole EGP (a multiple of 100 minor; the rounding applies to the money only). Checkout goes through the normal Kashier / InstaPay paths. The new package starts at once with the SAME period start and end (`grantUpgrade`: one guarded batch, only if the subscription is still on the package it was priced from), and the credits switch from the CURRENT month: the entitlement event tops the month's grant up to the new allowance (used credits are kept, never wiped), later months grant the new allowance.
- *Downgrade* (a lower or equal yearly package, or any monthly package): paid in full, queued behind the running period (`grantQueuedSwitch`), starts as its own package and length at the next renewal; no refund of the running package.
- A QUEUED period cannot be switched: while one is queued, only a renewal of the running package is accepted (and nothing, if the queue holds a switch): `409 yearly_queued` (the copy names the brand's support email, ahlan@ebda.app for Ebda Chat, Ruling WA-SUPPORT-1; the operator cancels and refunds it, below).
- Every path is idempotent: the payment claim, the grant stamp and the guarded update key on the order and the provider reference, so a replayed payment or event applies once. Upgrade -> downgrade -> upgrade cannot yield a free month: the downgrade only queues, and a second switch is refused while anything is queued.

**Yearly refunds (Review Focus 5, WA-REFUND-1).** `yearlyRefundQuote`: a month is worth `floor(price / 12)` of the CURRENT package (after an upgrade: the higher plan's rate, because the difference for those months was paid); the unused whole months are counted up to the CURRENT `period_end` (a period shortened by earlier refunds has fewer); money already refunded beyond the months already cut is deducted; the result never exceeds everything paid for the period (the original order plus its upgrades) minus what was refunded. The month in progress is never refunded, so a refund in the last month is 0; the wallet's debt is settled FIRST out of the value. `GET /api/v1/operator/package-orders/:orderId/refund-quote` shows the figures (session re-checked, fails closed).
- A PARTIAL provider refund of a yearly order shortens the running period by `floor(cumulative refunded / monthly value) - months already cut`, capped at the unused months, and the end can only move EARLIER (`period_end = min(period_end, new end)`); less than a month's value shortens nothing and expires no credits. Monthly packages still shorten proportionally. A FULL refund of an upgrade order does not undo the upgrade: use the operator action.
- **The operator action** (console, Account tab: "Cancel a yearly plan and refund") calls `POST /api/v1/operator/package-orders/:orderId/yearly-refund {reason}`: it fixes the figures from the quote, records ONE plan per period (`package_refund_plans`), CANCELS the subscription at the end of the current month (still in effect until then), adds the debt part to the order's refunded total, then credits the wallet debt as a ledger row `yearly-refund-debt:<order>` (idempotent). The cash part is `cashRefundMinor`, sent through the provider's dashboard; its webhook adds to the refunded total and shortens nothing more. If the debt is at least the value of the unused months, `noMoneyOut` is true and nothing is sent. A replay returns the same answer and posts nothing twice. A store owner or staff gets 403.
- A refund webhook retried after the store-plan fallback is safe: the credit expiries are ledger rows with fixed refs (`expire:refund:<order>`), so a replay changes no balance.

**Second review of P2 (all pinned in `test/packages-yearly-upgrade-refunds.test.ts`):**
- A full refund of an UPGRADE reverts the package only in the period the upgrade was GRANTED in (`period_start = quoted_period_start`) and only if it was granted; an upgrade of an earlier period, or one paid and never granted, is just closed. The credits it added (the month's grant above the old package's allowance) expire with it, unused ones only (`expire:upgrade-refund:<order>`).
- A full refund of the order that OWNS a period leaves any upgrade paid on top of it unrefunded: one P1 `upgrade_stranded_by_owner_refund` per upgrade (a person refunds or keeps it).
- The operator refund is refused while anything is queued behind the period (`queued_periods`: cancelling would strand the renewal) and for a queued order itself (`order_queued`: refund its whole payment through the provider, which removes just that period). The refund QUOTE returns the same two refusals, so it never offers what the action refuses. The plan is recorded only if the money already refunded across the period and the period itself are unchanged since the quote (otherwise `quote_changed`: ask again).
- An upgrade is granted only in the SAME calendar month it was quoted in, and never when its order had expired; a payment that arrives later is recorded (`paid`, with the transaction, so a refund can match it) but not granted, and raises ONE P1 `switch_order_stale` (not one a day).
- Only a period whose `source` is `purchase` is a yearly order's: an operator or Store-plan write clears `owns_running` in the same batch, and `periodBasis` also checks the source.
- A partial refund is counted at the rate in effect WHEN IT WAS MADE (`package_refunds.cut_value_minor`), so months cut before an upgrade are not re-priced at the higher rate afterwards.
- The wallet credit of an applied plan's debt part is posted by the daily repair if the call failed after the D1 batch (`package_refund_plans.debt_posted`, the fixed ref makes it land once); a failure alerts `yearly_refund_debt_not_posted`.
- **Residuals (not verified live):** the Kashier checkout session expiry (how long a quoted checkout stays payable; the month guard above bounds the damage) and Kashier's per-transaction refund cap (a refund larger than the cap must be split by the operator; the cumulative logic does not depend on it). Verify both on the first real yearly sale and refund.

## Package limits and feature gates (WA-PRICE-1, migration 0014)
Seeded packages (EGP minor per month; Meta fees are never included): `starter` 69000 (300 AI credits, 2 members), `growth` 149000 (1500, 5 members, + campaigns and ordering in chat), `pro` 349000 (5000, 15 members, + API and priority support); `store-included` stays 0 (100 credits, 2 members, no paid-tier feature). Limits are D1 columns on `packages` (`max_members`, `feat_campaigns`, `feat_order_in_chat`, `feat_api`, `priority_support`). They travel in the entitlement event as `limits`, whose default is the DENY shape (1 member, no feature), and the workspace keeps them in its own `entitlements` copy (DO migration v32). The daily reconcile re-sends the current version, and an event of the SAME version refreshes the limits (and only the limits) when it carries them, so a copy written before limits existed picks them up.
Gates read the workspace copy on every request (never cached): `featureAllowed(sql, 'campaigns' | 'order_in_chat' | 'api')` is true only with an entitlement row, status trialing or active, and the limit on; `memberLimit(sql)` is 1 without one. `403 plan_feature {feature}`: campaigns create / send / resume; a running campaign pauses at its next page with `plan_blocked` after a downgrade (nothing already queued is reversed; pause and cancel stay open); the ordering bot stops (`orderingActive` also needs `order_in_chat`, so the plain inbox path answers); a client (integration) token needs `api` on every route including `GET /me`, and an unregistered workspace is refused without creating a Durable Object. Documented residuals: messages already queued for a campaign page still send after a downgrade (nothing is reversed; only the next page, a send, a resume and the scheduled start are refused, for every template category); an integration WebSocket opened before a downgrade keeps streaming until its token expires (at most 10 minutes), because the plan is checked when a connection or request starts. The same-version limits refresh is safe only because no code edits a package's limit columns after the seed; a future editor of them must bump the version of every subscription that uses the package. `GET /packages` returns `maxMembers`, `features` (keys in the order members, shared_inbox, order_confirmations, templates, campaigns, order_in_chat, api, priority_support, ai_credits) and `periodMonths` (1).
Team seats (Ruling WA-SEATS-1, `src/core/seats.ts`, `src/routes/members.ts`): the package's `maxMembers` counts the owner, so there are `maxMembers - 1` staff seats. Membership is the Store's (identity contract v1.4, Ruling ID-19), read over the `STORE_BRIDGE` service binding (`memberRole`, `listStoreMembers`; the adapter in `src/addons/ebda/store-bridge.ts` is the one place that calls them); the DO table `seats` (migration v39) only records which staff the owner seated. In `requireStoreAccess`, a person who is a member by token is checked against the Store's LIVE role on EVERY request (never cached): no answer is `503`, not a member is `403 no_seat`, and the effective role is the LOWER of the token's and the Store's; staff must also hold a seat that is inside the package's capacity (`seatState`: the earliest `(assigned_at, user_id)` rows up to `maxMembers - 1` are `seated`, later rows `over_limit`, no row `none`), else `403 no_seat`. A plan not in effect has limit 1 (the owner alone). Routes, owner only: `GET /stores/:id/members` (the live team, each seat, `{ limit, used, overLimit }`; drops the rows of people who left the Store), `PUT /stores/:id/members/:userId/seat` (201, 200 if already seated, `403 seat_limit {limit}`, 404 `not_a_member`, 400 for the owner), `DELETE .../seat` (204, idempotent). A downgrade deletes nothing: seats beyond the new limit become `over_limit` and raise the INFO alert `seats_over_limit`. Without a Store link (a white-label deploy, no binding) there is no membership source and seats are not applied. A person with an integrator token or a super admin is not subject to seats.

## Packages: three writers, one place (`PACKAGE_CHECKOUT_ENABLED` for purchase)
A workspace's package is D1 `workspace_subscriptions`, written ONLY in `src/core/billing/subscriptions.ts` (`setSubscription`, `cancelSubscription`, `rollRenewals`). Each write is one D1 batch: the row is upserted with `version = version + 1` in the same statement (racing writers never share or lower a version), `source` (`store_plan` | `operator` | `purchase`) is recorded, and a `billing_audit` row (`subscription_set`, ref = event id / operator user id / order id) is appended only if the row changed. Only after the batch commits does `announceSubscription` push `applyEntitlement` to the workspace and queue `whatsapp.entitlement_changed {packageId, automation, status, validUntil, version}` (event id = f(workspace, version): announcing again is harmless). A failed push is healed by the daily reconcile; a failed Store queue is logged (`entitlement_event_not_queued`) and never undoes the write.
Rules live in SQL, never read-then-write: the SAME package written again while it runs keeps `period_start` (its AI credits are neither refilled nor expired; only the end moves); a different package, or one that has ended, starts a new period now. Package AI credits are valid for their period only and never carry over.
1. **Store plan** (`store.plan_changed`, `billing/store-plan.ts`, in the queue consumer): the event is first CLAIMED in `store_plan_applied` (not older than the last applied `effectiveAt`, not the last event id) inside the same batch as the write, so replays and out-of-order events write nothing. `includesWhatsApp=true` -> package `store-included` (price 0, 100 AI credits, seeded by migration 0008) with the event's `status`/`periodEnd`, else active until `effectiveAt` + 31 days. **The period is the Store's billing period, not the event (C12 / wa#117, Ruling WA-STORE-PERIOD-1):** a store-included row that already covers the same Store `periodEnd` keeps its `period_start`, so a past_due -> active flip, a failed charge then a paid retry, or any repeat inside one Store period never starts a new period (which would expire the grant and grant 100 fresh credits); a renewal moves `periodEnd` and is a new period. Cost if wrong: a Store that re-sends a changed `periodEnd` inside the same month (e.g. a period-end correction) still starts a new period and grants once more. `false` -> cancels it. A running purchased or operator package is never replaced or cancelled by the Store plan (checked in the write's SQL). The marker also remembers what the Store plan says, so when a bought/operator package ends, the daily reconcile (and a refund) hands the store back to `store-included`.
2. **Operator**: `PUT /api/v1/operator/workspaces/:id/subscription {packageId, status, periodEnd, reason}` (super admin, session re-check fails closed, 404 for an unknown workspace/package, audited, immediate). Extending the same package keeps its period and credits; a different package starts a new period. Rows that existed before migration 0008 are operator-owned.
3. **Purchase** (owner): `GET /stores/:storeId/packages`, `POST /stores/:storeId/packages/:packageId/checkout` (no body needed; the amount is `packages.price_minor`, never from the client; session not revoked, fail closed; the checkout URL must be on the Kashier checkout origin) writes a pending `package_orders` row; `GET /stores/:storeId/packages/orders/:orderId` only reads and says `paid` only once the package was granted. Every route is 404 while the switch is off. The existing `POST /kashier/webhook` dispatches on the order id. A SUCCESS with the stored amount/currency runs ONE batch: claim (pending|failed|expired -> paid, `provider_ref` unique), subscription write only if the claim holds and `granted_at IS NULL`, stamp `granted_at`. Either all of it commits or none does; a retry after a lost response only re-announces. A second SUCCESS with another transaction id on a paid order grants nothing, alerts `package_duplicate_payment` and is recorded in `billing_audit`. Amount mismatch -> `package_amount_mismatch`, no grant. No card fee is added to a package. A payment that arrives after the order expired is still granted.
4. **Renewal is manual, and an early renewal queues**: the package runs its month. Buying the SAME package while it runs does not touch the running period or its credits: one `queued_periods` is added (one payment = one extra period). Each order records what it paid for: `owns_running` (the order that owns the running period) or `queued_seq` (its place in the queue); an order with neither paid for a period that has ended. At the old `period_end` the workspace's `subscription_expire` task asks the control plane to roll the queue (`rollRenewals`): the new period starts at the old end with a fresh grant, the unused old credits expire. The daily reconcile rolls any that were missed. Buying a DIFFERENT package replaces the running one now (new period, upgrade rule above). 7 days before the end the inbox banner shows a renew line (not for `store-included`).
5. **Provider refund / chargeback** of a package order (the refund is its own transaction; each is applied once, keyed by its transaction id in `package_refunds`):
   - **Full** (cumulative refunds reach the order amount; alert `package_refunded` / `package_chargeback`): the order becomes `refunded` / `charged_back`. If it owns the running period and nothing is queued, the plan is `cancelled` with `period_end = now` and a higher version (pushed, announced to the Store), the unused part of that period's grant is zeroed with a ledger `expire:refund:<orderId>` row (used credits stay used, purchased credits are never touched, every expiry is counted against the period's grant so a partial refund followed by a full refund, a period end or another partial refund never expires the same credits twice; nothing is deleted; if that step fails the webhook answers 5xx and the retry does it, once), and a store whose Store plan includes WhatsApp falls back to `store-included`. If it owns the running period and a period is queued, the running one ends now and the next queued period starts immediately (fresh grant). If it paid for a queued period, only that period is removed and later ones move up. If its period already ended, the plan is untouched.
   - **Partial** (alert `package_partial_refund`): the running period it owns is shortened by the refunded fraction (`new_end = max(now, period_start + (period_end - period_start) x (remaining - refunded) / remaining)`, where `remaining` is the order amount not yet refunded), the version goes up and the Store is told, and the same fraction of the period's unused credits expires (`expire:partial:<refundTx>`; the fraction is stored with the refund when it is decided and reused on retry). The full-or-partial decision is made inside the batch: the refund row is written only if the order still has the refunded total it was decided on, so two concurrent halves end as one full refund. A partial refund of a period that has not started changes no period (recorded in `refunded_minor` only).
6. **Daily** (`repairPackageOrders`): a `paid` order with `granted_at` NULL (should be impossible) is granted and alerted `package_paid_not_granted`; pending orders older than 24 h become `expired`.

## Top-ups (7.4), `TOPUPS_ENABLED=true`
`POST /wallet/topups {amountMinor}` (owner, session not revoked via the `ACCOUNTS` binding `isRevoked(sid)`; unbound -> 503) writes a pending D1 `topups` row and returns the hosted checkout URL. The merchant pays the card fee ON TOP (`KASHIER_FEE_BPS`, `KASHIER_FEE_FIXED_MINOR`); the wallet is credited the exact amount (WA-TOPUP-FEE-1). `POST /kashier/webhook`: HMAC-SHA256 (hex, constant-time) over exactly the fields named in `data.signatureKeys` (sorted, `key=encodeURIComponent(value)` joined by `&`; we require amount, currency, merchantOrderId, status and transactionId to be among them) (https://developers.kashier.io/docs/webhooks). **The top-level `event` label (`pay` / `refund` / `partial_refund` / `reversal`) is NOT signed, so it is never applied.** For an order of ours, before any money or entitlement effect, we ask Kashier for ITS record of the signed transaction id (`GET {KASHIER_API_URL}/v2/aggregator/transactions/:id`, `Authorization: <KASHIER_SECRET_KEY>`) and act on the kind (payment / refund / chargeback) and status Kashier reports; the signed amount, currency, order id and transaction id are kept. If Kashier cannot be reached, answers 404 (not there yet), reports another transaction/order/status or an unknown operation, the transaction id is not a plain `[A-Za-z0-9_-]{1,64}` id, `KASHIER_API_URL` is not https, or the secret key is not configured, the webhook answers 503 and nothing happens. The delivery is kept in `unconfirmed_webhooks` (only what re-verification needs: the fields named in `signatureKeys`, the signature and our order id) and the daily pass (`reconfirmUnconfirmed`) runs it through the same path as a live webhook, so the claim on the transaction id makes it one effect whichever confirms first. One attempt a day; every terminal outcome (credited, granted, failed, amount_mismatch, refund_refused, refunded, duplicate_success, ...) closes the row with that `resolution`; one still open after 24 h raises `webhook_unconfirmed_aged` once, and after 14 attempts it is `abandoned` with `webhook_unconfirmed_abandoned` once (the structured alert line the alert bridge turns into a notice, like every other money alert) and is no longer retried. Only open, due rows are read, so closed or abandoned rows never take a slot. A refund that is confirmed BEFORE its payment is credited or granted is kept open (`payment_pending`) and run again the moment the payment is credited, by whichever path credits it, so the two net out. A package refund that loses six races in a row answers 5xx and is kept (`refund_contention`) for the daily pass. Closed rows are deleted 30 days after they close. Checkout (top-ups and packages) refuses with 503 `unavailable` while the secret key is missing. Idempotency keys bind signed values only (`kashier:<transactionId>:<status>`). On top of that: a payment is accepted only if the order has no transaction yet or this one (a second, different success alerts `duplicate_success` and does nothing); a refund is accepted only if its transaction id differs from the payment's and the top-up is `paid` (a package order: `paid`) (else `refund_refused`). NOT verified live: the operation value of a refund in the details API and whether a transaction is queryable the instant its webhook arrives. SUCCESS + order id + amount + currency must match OUR row; the workspace comes from the row; credit ref `kashier:<transactionId>`; debt is settled first by arithmetic. The browser return (`GET /wallet/topups/:orderId`) only reads. Provider refund/chargeback -> negative `chargeback` row + alert. Secrets: `KASHIER_API_KEY` (Payment API Key: checkout hash + webhook HMAC), `KASHIER_SECRET_KEY` (a DIFFERENT key, the Kashier Secret key: authenticates the transaction-details confirmation), `KASHIER_MERCHANT_ID`; var `KASHIER_API_URL` (default `https://api.kashier.io`, test `https://test-api.kashier.io`). **Inquiry (daily repair of a lost webhook)**: `repairTopups` (pending top-ups older than 15 min, expired after 7 days) and `repairPackageOrders` (pending or expired package orders 15 min to 7 days old, only while `PACKAGE_CHECKOUT_ENABLED`) ask `PaymentProvider.inquire(orderId)`. Kashier's documented list call finds the payment by OUR order id (`GET {KASHIER_API_URL}/v2/aggregator/transactions?search=<orderId>&type=payment&limit=20`, `Authorization: <KASHIER_SECRET_KEY>`; https://developers.kashier.io/openapi.yaml `listTransactions`); only rows whose `merchantOrderId` equals our id are candidates and every one is confirmed with the SAME transaction-details call as the webhook (status, kind and order come from that record). A confirmed payment is applied through the webhook's own apply path (`applyTopupWebhook` / `applyPackageWebhook`: claim on the transaction id, amount and currency must match, so a repair racing the webhook, or running twice, is one credit or one grant). Kashier unreachable, an unclear answer, or several successful payments for one order (alert `inquiry_multiple_success`) change nothing and the order is asked again the next day; a wrong amount alerts (`topup_amount_mismatch` / `package_amount_mismatch`) and changes nothing; no payment found yet is simply pending. NOT verified live: the list row's amount field (`amount` or `totalAuthorizedAmount`), the checkout link and the refund call (see Refunds below).

## Card refunds and the refund webhook (`KASHIER_REFUNDS_ENABLED`, default off)
The wallet is debited ONCE per refund, at approval (`refund:<requestId>:<n>`). Everything Kashier reports afterwards about that money must be matched to it, never booked again. D1 `card_refunds` (migration 0010) has one row per refund transaction we know of, in WALLET units (`topups.amount_minor`; the card fee was never in the wallet and is never debited or refunded from it), written BEFORE Kashier is asked.
- **Off (default)**: Kashier's refund API is never called; every card chunk is a manual payout (bank / InstaPay), exactly as before.
- **On**: for each card top-up chunk (oldest first) a `card_refunds` row (`sending`) is written, then Kashier is asked once: `PUT {KASHIER_API_URL}/v3/payment/refund/{kashier order id}` `{apiOperation: "REFUND", reason: "refund-request:<id>:<n>", transaction: {amount}}` with `Authorization: <KASHIER_SECRET_KEY>` (https://developers.kashier.io/openapi.yaml `refundOrder`; the same operation as `PUT fep.kashier.io/v3/orders/{id}`, one hop closer, on the host we already allow-list). Kashier's order id is read from the paid transaction's details (`body.order.orderId`); without it nothing is sent and the chunk is manual. The row keeps the refund's own transaction id.
  - A clean `SUCCESS` (top-level status, `response.status`, operation `refund`, our amount, a plain transaction id) marks it refunded and adds to `topups.refunded_minor` in the same batch. `PENDING` stays `pending`. A clear refusal (4xx, FAILURE) or nothing sent (`unsupported` / `unavailable`) makes that chunk a manual payout.
  - Anything that might mean "processed" (timeout, 5xx, unreadable answer, another amount) is `uncertain`: the request stays `processing`, the call is NEVER repeated (Kashier documents no idempotency key; the request id is in `reason` for the operator), and a webhook, the refund status by id or the refund list settles it (`reconcileCardRefunds`, daily). Open for 3 days: alert `card_refund_stuck` once for a person to check Kashier's dashboard.
  - The request's split is derived from its rows (card = succeeded + linked, open = waiting, manual = the rest); `processing` while anything is open.
- **Refund webhook** (`topups.ts` -> `applyProviderRefund`): (1) the refund's id belongs to a row of ours and Kashier's own record says it is a card refund (`refund` / `partial_refund`) -> reconcile the row, no wallet movement (a chargeback / reversal / void carrying that id settles nothing and alerts `refund_id_conflict` P1); (2) else, for a real card refund only, an open API row of the same top-up with the same amount that has NO provider id yet -> bind the id, reconcile, no movement; (3) else a refund or chargeback we did not start -> ONE debit `chargeback:<refundId>` (replays post nothing) of its FULL amount in wallet units up to what the top-up credited (`amount_minor`; the card fee was never in the wallet and is never debited), the wallet may go into debt, and nothing already used by other refunds or open card refunds shrinks it. Beyond the credited amount, the card fee explains up to `fee_minor`; anything past that is recorded (`card_refunds.note`, `billing_audit` `refund_excess_review`) and raised as a P1 alert `refund_excess_for_review` for an operator, never dropped silently. A `FAILURE` webhook for our pending row makes it a manual payout.
- **Refunded in Kashier's dashboard** (a manual payout paid by refunding the card there): the operator links it, `POST /api/v1/operator/refund-requests/:id/link-dashboard-refund {kashierRefundId, amountMinor, orderId?}` (field in the operator refund queue). The link first asks Kashier (`type=refund` list + details): the id must be a `refund` / `partial_refund` for this top-up's order, SUCCESS, for exactly that amount, else `refund_not_verified` (503 `provider_unavailable` if Kashier cannot be asked); nothing is recorded on a refusal. The link itself moves no money. If the refund's webhook already arrived first and debited a second time, giving that debit back is a wallet credit and goes through the adjustment flow (`requestAdjustment`) with a SECOND approver at ANY amount (money moved from a manual action): a different super admin must approve; the requester cannot approve their own. The adjustment has the deterministic id `relink:<refund id>`.
- **Debit phase first**: an approval posts ALL its wallet debits (and writes every card refund row) before any provider call. If that phase aborts (the balance shrank), no provider call was made, the request stays `processing` with no manual amount (money that was never debited is never offered for payout) and alert `refund_debit_incomplete` (P1) asks a person to look. Only when the phase is complete (`refund_requests.debit_complete`) can the request become `manual_payout` or `paid`. The approval's PLAN (`refund_chunks`: amounts, refs, top-ups, transactions) is recorded once before any money moves; a resume of an aborted run replays that plan, never recomputing it from today's totals. One run at a time: the approval claims the request with a lease (`claimed_by`, `lease_until`, 5 min, compare-and-swap) and each card refund row is flipped `sending` -> `calling` by a guarded UPDATE before the provider is asked, so two runs (or two resumes) can never send the same row twice. The card refund rows of the whole plan are written in the SAME batch as the plan as `planned` (a reservation only: counted by every room sum together with `held` refunds, but invisible to the webhook matcher, the reconciler and mark-failed until the row's wallet chunk is posted and it flips to `sending`), so any other approval's planning sees them at once, and right before each provider call the guarded flip re-checks that the top-up still has room (`amount_minor - refunded_minor` minus the other open rows ahead of this one: already calling/pending/uncertain, or planned earlier); a row that no longer fits is NOT sent: it is failed by ONE atomic statement (re-checking it is still `sending` and still has no room, so a row another run just moved to `calling` is never failed), becomes a manual payout and raises `card_refund_over_refundable` (P1). Only an approval can resume; a **reject** only closes a request nobody has started (`pending`): abandoning a partly debited request is a separate operator flow that must first reverse the posted `refund:<id>:*` entries.
- **Abandoning a partly debited request** (`POST /api/v1/operator/refund-requests/:id/abandon`, super admin, session re-checked, two operators): for a request left `processing` with its debit phase incomplete. The first operator asks (recorded in `abandon_requested_by`); a DIFFERENT operator's call executes (the same operator again is `second_approver_required`). Execution is ordered so a concurrent resume can never also send: (1) ONE compare-and-swap moves the request `processing` -> `abandoning` under a fresh lease token (a live run or a concurrent abandon is `in_progress`; from then on no resume can claim it, and a run holding an older lease can neither post a chunk, complete its debit phase nor send a row: each of those steps checks that its token still holds the request); (2) only then the safety read: any row `calling`, `succeeded`, `uncertain`, `pending` or `linked` means money may have left (`money_may_have_left`) and the request goes back to `processing` untouched; (3) the `planned` and `sending` rows are failed by guarded UPDATEs (a row that no longer moves stops the abandon the same way); (4) only wallet chunks that were really posted (`refund:<id>:<n>` found on the ledger) AND whose row this abandon closed (or that never had a row) are credited back, once each, as an `adjustment` with the idempotent ref `refund-reversal:<id>:<n>`; (5) `abandoning` -> `abandoned` and the `refund_abandoned` audit row. The wallet post and the lease check live in different stores, so a debit can still land in the gap: it is closed from three sides with the same idempotent ref `refund-reversal:<id>:<n>`: the run re-checks the lease right AFTER each post and, if an abandon took over, reverses its own chunk and stops; the abandon runs a sweep after setting `abandoned`; and the daily pass sweeps every request abandoned in the last 30 days (`sweepAbandonedRefunds`, alert `refund_abandon_sweep_failed` P1). Whichever comes first reverses it; the others find the reversal and do nothing. ONE eligibility rule (`reversibleChunks`) serves all of them: a chunk is reversible only if it has NO card refund row or its row is `failed` with note `abandoned:<id>`; if ANY row of the request may have sent money (calling, succeeded, uncertain, pending, linked) NOTHING is reversed and `refund_reversal_blocked` (P1, once) is raised. A run reverses only once the request is `abandoned` (while it is `abandoning` the abandon owns the reversal). The sweep takes the oldest abandoned requests not yet marked clean (`swept_at`, ordered by `abandoned_at`, 200 per pass) and marks each one it finished once it is past a grace of twice the approval lease (10 minutes; until then every pass re-checks it, because a run whose lease ran out can still post a chunk just after the abandon), so a backlog is worked off across passes without starving older requests. Money first, flip last: a crash anywhere is finished by repeating the call, and a repeat after the end is a no-op. An abandoned request can never be run again.
- **Id mismatch trap (`refund_held`)**: our API refund is recorded with the id Kashier answered with (R). If Kashier's webhook names it with another id (W), a real card refund of the same top-up and amount, created within 7 days, whose refund (R) no webhook has confirmed yet, is HELD instead of debited: a `held` row, alert `refund_held` (P1, once per W), no wallet movement. An operator matches it (`POST /api/v1/operator/card-refunds/held/:refundId/match`): the candidate refund (`card_refunds.candidate_id`) must exist, be unconfirmed, in succeeded / pending / linked, on the same order and amount, and the guarded batch must change exactly that one row, else `not_verified` and nothing changes; Kashier must list W as a successful card refund for that order and amount; if Kashier lists BOTH W and the candidate's own id as separate successful refunds, money left twice: the match is refused (`separate_refund_debited`) and W is debited as an unknown refund (P1 `refund_held_debited`). A match marks our refund confirmed and moves no money. A chargeback or reversal is never held: it debits in full. **Verify R == W on the first live refund before enabling `KASHIER_REFUNDS_ENABLED`.**
- **A refund left `sending`/`uncertain`** (a crash, a lost answer): the operator can turn it into a manual payout (`POST /api/v1/operator/refund-requests/:id/card-refunds/:cardRefundId/mark-failed`) only after Kashier's refund list shows no successful refund of that amount for the top-up that another row has not claimed.
- **What stays on with `KASHIER_REFUNDS_ENABLED` off**: the double-debit fix is always on (it corrects a bug that predates the switch): the refund webhook is matched against recorded refunds and a refund or chargeback we did not start is debited once, its full amount up to what the top-up credited, with the excess and a refund that finds nothing credited raised as P1 review items (`refund_excess_for_review`, `refund_unmatched_no_credit`; the delivery is answered 200, never retried forever). The dashboard-refund link and the held-refund match are operator tools and need only the Kashier credentials. What the switch controls is exactly one thing: whether approving a refund asks Kashier to refund the card (off = every card chunk is a manual payout and no `card_refunds` row of source `api` is written).
- **The Kashier API origin is pinned**: `KASHIER_API_URL` must be https on `kashier.io` or a subdomain (`api.`, `test-api.`); any other value makes every call (inquiry, confirmation, refund) refuse before a request is made, so the secret key is never sent elsewhere.
- NOT VERIFIED live: Kashier's refund response shape, that the dashboard-host route accepts the order id from the details, PENDING behaviour, the refund webhook payload (the docs list the event names only) and that refund rows carry the original merchant order id. Check the first real refund (`docs/launch/README.md`).

## Daily passes drain (M-178) and the InstaPay duplicate / proof rules (W2-MONEY: C2, M-096)
- **Drain.** `src/core/billing/drain.ts` `drainKeyset`: every daily money pass (`repairInstapay`, `overdueInstapay`, `purgeInstapayProofs`, `reconcileCardRefunds`, `sweepAbandonedRefunds`, `repairTopups`, `reconfirmUnconfirmed`, `repairPackageOrders` both loops, `repairRefundPlans`, `reconcileRefundBounds` (both tables) and the offboarding pass) reads page after page with a KEYSET cursor until a page is short, instead of `LIMIT 100` and stop. A row that keeps failing is visited once per pass (the cursor moves on). A pass is bounded to 50 pages (5,000 rows at the default size); beyond that it stops, raises `billing_pass_backlog` (P1) and the next daily pass continues (the queries select by state, so finished rows drop out). A handler that throws raises `billing_pass_row_failed` (P1) and the pass continues.
- **Same proof image (C2).** The upload stores the SHA-256 of the file (`instapay_requests.proof_sha256`, kept after the image is deleted). If another request (any workspace, or the same one twice) in `under_review` or `confirmed` has the same hash, the NEW request is held (`held_reason = 'duplicate_image'`, `held_of` = the first twin); an earlier twin still under review is held too (nobody can tell which is honest); an already confirmed one is left alone. P1 alert `instapay_duplicate_proof`, audit `instapay_held`.
- **Same bank reference (C2, DUP-REF-REQUIRED-1).** The bank's own transaction number from the proof is REQUIRED at confirmation for every amount (`bankRef`, normalised: no spaces or dashes, upper case, 4 to 40 letters and digits). It is unique across all confirmed requests (a partial unique index, so a race loses too): a re-used one is refused (`duplicate_reference`) and holds the request, same alert. A proof that truly shows no number is confirmed only with the operator's audited `noReference: true` plus a reason of 5+ characters (console: a tick "The proof shows no reference number" and a reason box). Every such confirm is stored (`instapay_requests.no_reference`), recorded in `billing_audit` (the reason in `audit_reasons`, by `reason_id`) and raises the INFO alert `instapay_no_reference`; a SECOND no-reference confirm for the same workspace and the same amount within 7 days is HELD (the check is also inside the claim UPDATE itself, so two concurrent confirms cannot both credit) (`duplicate_reference`, P1 `instapay_duplicate_proof`). A two-approval amount (>= 1,000 EGP) can never skip the reference.
- **A rejected request frees its reference.** The first approval keeps the typed reference in `pending_bank_ref`; a rejection (and an expiry) clears it in the same UPDATE, and the duplicate checks ignore rows in a terminal state (`rejected`, `expired`) even if they still carry one, so a reference can no longer be blocked for ever by a request that never paid.
- **Held.** A held request cannot be confirmed (`409 held`); it can be rejected, or released by an operator who did not create it, with a reason of 5+ characters (`POST /operator/instapay/:id/release`, audit `instapay_released`). The queue shows the reason and the other request.
- **Proof lifecycle (M-096).** `purgeInstapayProofs` (daily) deletes the proof file 180 days after the decision (`PROOF_RETENTION_MS`), clears `proof_key`, keeps the hash. An undecided request keeps its proof whatever its age. A refused R2 delete keeps the reference and alerts `instapay_proof_purge_failed` (P1); tomorrow retries.

**Ruling PROOF-RETENTION-1 - 180 days after the decision.** It covers the longest realistic bank dispute window. Cost if wrong: a dispute after 180 days cannot be settled from the image; the bank statement and the stored amount, reference, deciders and dates remain.
**Ruling DUP-HOLD-1 - a duplicate is held, never silently confirmed or rejected.** A re-used transfer is either fraud or a merchant's honest second upload; only a person with the bank app can tell. Cost if wrong: an honest merchant waits for a release (the 4-business-hour SLA applies to the release too).
**Ruling DUP-REF-REQUIRED-1 (replaces DUP-REF-OPTIONAL-1) - the bank reference is required at confirmation for every amount, unless the operator ticks an audited `noReference` with a reason.** Evidence: `test/instapay-review.test.ts` ("900 EGP confirmed three times with re-encoded screenshots"). The image hash is exact, so a re-encoded screenshot of one transfer defeated it below the 1,000 EGP two-approval threshold (900 EGP confirmed 3x = 2,700 EGP credited for one transfer). Cost if wrong: an operator has to read one more field off every proof, and a proof with genuinely no number costs a tick, a reason and an INFO alert; a second such confirm for the same workspace and amount within 7 days waits for a release. If operators tick the box by habit the control degrades to the old image-hash-only check, which is why the INFO alert exists (review its count weekly).

**Ruling SOD-RELEASE-1 - EVERY release of a duplicate hold is kept (D1 `instapay_releases`, append-only: actor, reason, the held reason and the twin it reviewed). Nobody who ever released a request may first-approve or confirm it (`releaser_cannot_approve`), and nobody who first-approved it may release it (`approver_cannot_release`).** Also guarded in the SQL writes: the first-approval UPDATE and the confirm claim carry `held_reason IS NULL AND NOT EXISTS (release by this actor)` and their `meta.changes` is checked, so a race or a missed JS check cannot let it through. One person must not clear the fraud flag and also credit the money, however many times the request was held and released in between. Cost if wrong: with a small team a release needs a second operator even for an obvious false alarm.
**Ruling RELEASE-PAIR-1 - a release clears only the pair it reviewed (`twin_of`).** A NEW duplicate (another request id with the same image) holds BOTH requests again and alerts, whatever was released before, at upload and again in `confirmInstapay`'s own re-check. Cost if wrong: a third use of one transfer image costs another review.
**Ruling REF-UNIQUE-1 - the bank reference is unique among confirmed requests by a PARTIAL unique index over the new column** (`bank_ref`, NULL on every existing row, so the index cannot fail to build on production data; `test/migration-0020.test.ts` replays the migrations on seeded rows). A duplicate normalised reference at an approval is checked first in the same conditional UPDATE (first approval and confirm claim carry `NOT EXISTS (other request with this reference)`) and answers HELD + alert `instapay_duplicate_proof`, never a constraint error; the index is the unreachable backstop (its violation is also turned into a hold). Cost if wrong: a typo that equals another request's reference holds a genuine request until a person releases it.
**Ruling REF-TWO-STEP-1 - for amounts that need two approvals the bank reference is REQUIRED at both, stored at the first (`pending_bank_ref`), repeated identically by the second (`reference_mismatch` otherwise), and the duplicate-reference check (confirmed or pending refs on other requests) runs at both.** Cost if wrong: a proof that shows no transaction number cannot be approved above the threshold; the operator rejects it and the merchant re-sends a clearer one.
**Ruling ATOMIC-HOLD-1 - the duplicate-image hold is computed inside the UPDATE that moves the request to review, and `confirmInstapay` re-checks twins before it claims** (a twin that is not held is held then and refused as `held`, unless a person already released the request). The follow-up write that holds an earlier twin may fail; nothing can then be confirmed unheld. Cost if wrong: none beyond an extra read per confirmation.

## InstaPay billing (`INSTAPAY_BILLING_ENABLED`, default off)
The launch payment method for packages AND wallet top-ups until Kashier is approved; Kashier stays behind its own switches. Copies the behaviour of Ebda Store's "pay with InstaPay" flow (transfer, reference, proof, a human confirms).
- **Merchant (owner only, session revocation-checked like top-ups; staff get 403)**, `GET|POST /api/v1/stores/:storeId/wallet/instapay`, `PUT .../wallet/instapay/:requestId/proof`. `POST {kind: 'package', packageId}` or `{kind: 'topup', amountMinor}` (strict body; **the amount is computed on the server**: `packages.price_minor`, or the top-up amount within the card top-up min/max; at most 5 open requests). The answer carries the payee (`handle`, `name`, optional `qrUrl`), the exact amount, a unique human-typable `reference` (`WA-` + 8 characters without 0/O/1/I) and an expiry 48 h ahead. Payee details come from the brand pack (`instapayPayee`: the Ebda pack maps `EBDA_INSTAPAY_HANDLE` secret, `EBDA_INSTAPAY_QR_URL` and `EBDA_INSTAPAY_PAYEE_NAME`, the same values `ebda-api` uses, so `src/core` never names them); a brand without them gets no InstaPay billing (503, fail closed), never an empty address.
- **The proof**: jpeg / png / webp / pdf, at most 5 MB, checked by size and by magic bytes (the bytes decide, a lying content type or SVG/HTML is 415, over 5 MB is 413), stored PRIVATE in R2 under `instapay-proof/<workspace>/<request>.<random>.<ext>` (a unique key per upload: a losing double-submit deletes only its own object; the winning key is stored on the row in the same conditional UPDATE) (no public route and the media routes do not know the key). A proof uploaded after the 48 h expiry is refused. States: `awaiting_proof` -> `under_review` -> `confirmed` | `rejected` (with the operator's reason, shown to the merchant in the Wallet screen), or `expired`.
- **Operator (super admin, writes re-check the session, audited in `billing_audit`)**, `GET /api/v1/operator/instapay?state=`, `GET .../instapay/:id/proof-link` (a link signed with HMAC under its own key (HKDF-SHA-256 from `TOKEN_ENC_KEY`, info `instapay-proof-link`) that works for 2 minutes and names one request; issuing it is audited; PDFs are served as attachments because a sandboxed inline PDF does not render in Chrome; this and the review list re-check the session like a write, because proofs are personal data), `POST .../instapay/:id/confirm`, `POST .../instapay/:id/reject {reason}`. **Maker-checker**: the person who made the request never confirms or rejects it; at or above `ADJUSTMENT_APPROVAL_MINOR` a second, different operator must confirm (the first records `first_approver`). Every transition is one conditional UPDATE, so confirm, reject, expiry and upload racing each other end in one outcome.
- **Effects, exactly once, through the card payment's own paths**: the request writes its order in the same batch (a `package_orders` row or a `topups` row with `provider = 'instapay'`, no card fee). Confirmation runs `grantOrder` (-> `setSubscription` + the `whatsapp.entitlement_changed` event, ref `instapay:<reference>`) or the top-up credit (wallet post with the ledger outbox, ref `instapay:<reference>`); the unique reference, the claim on the order and the idempotent ref make a double confirm, a retry or the daily `repairInstapay` (a confirmed request whose grant did not finish, alert `instapay_confirmed_not_granted`) grant once. A request whose amount no longer matches its order is refused (`instapay_amount_mismatch`, P1). The Kashier repair and expiry passes ignore `provider = 'instapay'` orders; an InstaPay top-up has no card, so a refund of its share is a manual payout.
- **Daily**: `expireInstapay` (no proof in 48 h), `repairInstapay` (its failure alert fires once per request), `overdueInstapay` (backstop). The SLA itself is a **one-shot check scheduled when the proof arrives** (the workspace Durable Object's scheduler, task `instapay_overdue`, due 4 business hours later via `addBusinessMs`), so the alert is not a day late; there is no hourly cron.
- **Review SLA**: 4 business hours (Sunday to Thursday, 09:00-17:00 Africa/Cairo, computed with Intl so daylight saving is right). The operator console shows it; a proof pending longer raises `instapay_proof_overdue` (severity P1) once. A rejection reaches the merchant in the app: the wallet carries `instapayNotice` (the owner's newest unseen rejection, with the reason) which the inbox banner shows until the owner opens the InstaPay card; no approved utility WhatsApp template exists for it, so there is no WhatsApp message yet. The cap of 5 open requests per workspace is part of the insert (one statement).
- Alerts: `instapay_proof_overdue`, `instapay_confirmed_not_granted`, `instapay_grant_failed`, `instapay_amount_mismatch`, `instapay_repair_failed`, `instapay_expiry_failed`, `instapay_overdue_check_failed`.


## InstaPay auto-confirm (default OFF; rulings INSTAPAY-AUTO-1.*, foundation INSTAPAY-1..7)
A proof that passes every check confirms and grants by itself (actor `system:auto-confirm`); anything else waits for a person exactly as above.
- **Switches** (D1, read on every decision): global mode `off | shadow | live` (`PUT /operator/instapay/auto/mode`, default off; shadow decides without activating), per-workspace (`PUT /operator/instapay/auto/workspaces/:workspaceId`). Each needs a reason and is audited. A revert switches that workspace off.
- **Checks** (`decideInstapay`): amount equals the server amount exactly, payee is our handle, transfer within 48 h (Cairo time), reference and image never seen anywhere (shared D1 `INSTAPAY_DEDUPE_DB`, with the Store), first payment at most one month of the plan, below the two-approver threshold, not edited, no instruction-like text, confidence >= 0.8. Only a purchase that starts a period is automatic.
- **Digest**: the daily pass sends one message through the OS brain (`BRAIN_BRIDGE_URL`, HMAC `INSTAPAY_BRIDGE_SECRET`, direction `notify`); a waiting notice goes immediately for anything a person must review (not in mode off). The owner's "not received" tap calls `POST /internal/instapay/auto-confirm/not-received` (HMAC direction `revert`, replay-safe) or `POST /operator/instapay/auto/:id/revert`.
- **Revert**: unpaid + 48 h grace (`workspace_subscriptions.payment_unconfirmed_until`, the period ends there), unused credits of that payment removed (wallet `instapay-revert:chat:<id>:wallet`, AI `...:ai`), reference + image burned. Tables: `instapay_auto_confirmations`, `instapay_auto_settings`, `instapay_auto_workspace` (D1 0033). Alerts: `instapay_auto_digest_stale` (P1), `instapay_auto_error` (info).
- **Shared index on every confirmation**: a person's confirm with a numeric bank reference claims the shared index too (a receipt it already holds is held, never confirmed); a rejection releases the claim; `POST /operator/instapay/auto/backfill` (reason) burns every already-confirmed reference + image once (idempotent). First-payment cap is cumulative until a digest is sent (INSTAPAY-CAP-1); a top-up revert never takes money that arrived later (INSTAPAY-REVERT-1).
- `/health` returns `instapayAuto: { ready, missing }`; not ready = auto-confirm refuses to run.

## Merchant money surfaces (self-service A9 Chat half, A21, A22; migration 0034)
Three owner-only merchant actions, each as TWO calls: a **preview** that issues a confirmation, then the action carrying it. The confirmation (`core/billing/confirmation.ts`, D1 `money_confirmations`) is server-issued, single-use, expires after 15 minutes, stores only the SHA-256 of the token, is bound to the workspace + user + action from the session, and to the hash of the exact payload previewed. Replay -> `confirmation_used`; an edited or moved payload -> `confirmation_mismatch` (preview again); another store's or an unknown token -> `confirmation_missing`. One open confirmation per workspace + user + action (a new preview replaces it). Staff and other stores get 403/404 before anything is read.
- **Who pays Meta for an own number (A21)**: `POST /stores/:storeId/numbers/:phoneNumberId/funding/preview` and `PUT .../funding`, body `{funding: 'merchant_card'}` (+ `confirmId`, `token` on the PUT). The number must be in this store's own `phone_numbers` (the shared number and other stores' numbers are 404). `platform_line` is refused to a merchant with 403 `platform_line_is_operator_only` on both calls; a number the operator put on the platform line answers 409 `operator_funded` and is not taken back (one conditional upsert, so a race with an operator write cannot overwrite it). The write is audited (`billing_audit` `number_funding_set_by_merchant`) and the workspace's pricing copy is refreshed at once. The operator route stays (the only way to set `platform_line`).
- **Yearly package refund request (A22)**: `GET /stores/:storeId/wallet/yearly-refund` (quote + any request), `POST .../yearly-refund/preview`, `POST .../yearly-refund/requests {confirmId, token}`. The quote IS `packageRefundQuote`, the function the operator's refund-quote route and `executeYearlyRefund` call, so it equals what the operator would execute at that moment (test). The confirmation binds the order and every figure shown. Confirming writes ONE `yearly_refund_requests` row (`id` = confirmation id; one pending per store) and nothing else: no subscription change, no wallet row, no card refund (test asserts all four are unchanged). The operator lists waiting requests (`GET /operator/yearly-refund-requests`), runs the existing yearly refund, which closes the request. Nothing offered when the month is the last, the package is monthly, or a renewal is queued.
- **AI credit packs (A9, Chat half)**: `GET /stores/:storeId/wallet/credit-packs`, `POST .../credit-packs/preview {packId}`, `POST .../credit-packs/orders {packId, confirmId, token}`, `GET .../credit-packs/orders/:orderId` (read only). Packs are 100 / 500 / 1000 credits. **Ruling CREDIT-PACK-PRICE-1**: price per credit = the dearest per-credit rate among active paid monthly packages (rounded up to a piaster) times the pack size, so a pack never undercuts upgrading and no price table exists to drift; the order stores the amount it was created with and the webhook checks exactly that. Needs `TOPUPS_ENABLED` and a card provider that can confirm webhooks (else 503, nothing written). Order id `cp_<confirmation id>` (the single-use confirmation is the idempotency key: a double click is one order); a failed provider session closes the row `failed`. Credits are written ONLY by the verified webhook (the same `POST /kashier/webhook`, dispatched on the order id) or the daily inquiry (`repairCreditOrders`, 15 min to 7 days): the order is bound to ONE transaction id, then ONE append-only credit-ledger row `kind purchase`, ref `credit-pack:<transactionId>`, is posted, so a redelivery, a repair racing the webhook or a second payment on the order credits at most once. A wrong amount credits nothing (`credit_pack_amount_mismatch`, P0). A confirmed provider refund (**Ruling WA-PACK-REFUND-1**) expires the UNUSED part of the pack automatically (`expirePackUnused`: consumption draws on the period grant first, so the pack's remainder is the available balance beyond the grant's unused part, capped at the refunded share of the pack, a partial refund takes only its share; one `expire` ledger row, ref `credit-pack-refund:<orderId>:<refund transaction>`, parent_ref `pack:<orderId>`, never negative); the refund is FIRST recorded as one D1 row (`credit_order_refunds`, migration 0036, PK = `<orderId>:<refund transaction>`, so a redelivery is the same row) even when the pack was not credited yet, and crediting (payment webhook or the repair job) then credits and immediately expires under the same refund refs, so a refund that beats the payment leaves the balance at its unrefunded share (alert `notCredited: true`). The daily `repairCreditOrders` also runs `repairRefundExpiries` (migration 0037, `credit_order_refunds.applied_at`): a recorded refund of a PAID order whose expiry never reached the workspace (the step failed after the order was marked paid; the provider may never resend) is applied by the job, exactly once per refund (the expiry is keyed by the refund's ref, and `expirePackUnused` stores its answer under that ref in the workspace (`store_state` `pack.refund:<ref>`, written even when it expired 0) and also honours an existing ledger row under the ref, so the workspace is the source of truth and a missing `applied_at` backfill (none exists: the ledger lives in the workspace) can never double-expire; the job stamps `applied_at` after the check; `applied_at` stops re-visits; a refund of an unpaid order is left to crediting); the SPENT part is never reversed and stays for an operator. `credit_pack_refunded` (P1) still fires with `packCredits`, `expiredCredits`, `spentCredits`. Purchased credits roll over (only granted credits expire). The low-credit warning (inbox banner and Wallet) links to the Wallet card.

## AI credits: what one is, and when it is "low" (M-084)
- **A credit is one customer-visible AI reply**: one customer message the agent takes on and answers. One credit buys at most **4 model calls** (up to 3 rounds that use tools, then the call that must answer: `MAX_MODEL_CALLS_PER_CREDIT`, so a reply that fans out into tools cannot cost 5x what the price table assumes). Not per token, not per reply length, not per tool call (`AI_TURN_CREDITS = 1` in `src/core/ai/credits.ts`). A turn whose reply the guard replaces with a handover (`guarded`) or that ends in a handover after the model ran still costs its credit, because the model was paid for; a handover BEFORE the model costs nothing. Free: a message handed to a person before the model (a "talk to a human" request, no credits left, misconfigured), the "text only" note, a replayed task (charged once), every turn of a workspace with its own model key.
- **What a turn costs the platform is measured, not assumed**: every turn writes its token use to Analytics Engine; the query that turns it into a cost per reply and per workspace is in `docs/analytics.md`.
- **Cost per credit is logged per workspace and alerted per plan.** Each turn computes the platform's cost in EGP (tokens x the model's per-million prices `AI_PRICE_INPUT_USD_PER_M` / `AI_PRICE_OUTPUT_USD_PER_M` x the workspace's FX) and writes it to Analytics Engine next to the tokens (`double6`, EGP micros; 0 = unknown or the merchant's own model key). A rolling average per workspace raises the P1 alert `ai_cost_over_threshold` (once a day, after at least 10 turns) when it passes **half the plan's break-even per credit: Starter 1.00, Growth 0.45, Pro 0.33 EGP** (the yearly twins the same; `store-included` has no threshold). Break-even per credit is package price / credits (Starter 2.30, Growth 0.99, Pro 0.70 EGP) less card fees and Cloudflare (Pro about 0.67). The model prices in `wrangler.jsonc` (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`: 0.293 USD per million input tokens, 2.253 per million output tokens) were verified 2026-10-27 against https://developers.cloudflare.com/workers-ai/platform/pricing/; re-check them there and change the vars whenever the model (`AGENT_MODEL`) or Cloudflare's price changes. Unset prices = cost unknown, no alert. A voice-note turn adds the audio's cost: minutes x `AI_STT_PRICE_USD_PER_MIN` (`@cf/openai/whisper-large-v3-turbo`, 0.000513 USD per audio minute, verified 2026-11-12 at https://developers.cloudflare.com/workers-ai/models/whisper-large-v3-turbo/), always the platform's cost, also when the merchant uses their own model key; the turn still uses one credit.
- **Low credits** = the available credits (balance minus held) are under a tenth of the package's monthly allowance, never under 5 credits (`lowCreditsThreshold`): 100 -> warns at 10, 300 -> 30, 1500 -> 150, 5000 -> 500. The wallet view says it (`aiCredits.low`, `lowThreshold`, `allowance`; the Wallet screen shows a line), and the INFO alert `ai_credits_low` fires once a day while it holds. At zero the agent hands customers to a person (`agent_no_credits`).
- **Low wallet balance** is no longer a flat 20 EGP (about six marketing messages): it is `max(20 EGP, 3 days of the last week's average Meta spend)` (`LOW_RUNWAY_DAYS`), returned as `lowBalanceThresholdMinor`, and `wallet_low_balance` fires once a day while the available balance is under it.

## Refund bounds and indexes (W2-D1: M-057, M-138)
- **Indexes** (D1 `0021_indexes_and_refund_bound.sql`): `phone_numbers (workspace_id, status)`, `refund_requests (workspace_id, state, created_at)`, `billing_audit (workspace_id, id)` were scans; `test/d1-indexes-bounds.test.ts` runs `EXPLAIN QUERY PLAN` on the queries the code issues (a SEARCH on an index, never a SCAN) and walks the schema: every table with a `workspace_id` column has an index that leads with it or is listed with the key it is read by.
- **Ruling MONEY-FACT-1 (full text and evidence: `docs/launch/README.md`, "Money rulings (W2-D1)") - never reject an external money fact (a provider refund/chargeback): post the debit or revocation from the event amount, independently of bookkeeping; clamp `refunded_minor`; record any excess in full and alert `refund_exceeds_charge` (P1); hold the bound with a CI guard over the writers plus a daily reconcile, never a production ABORT.** A provider refund or chargeback is recorded in full and acted on from the EVENT's amount (the wallet is debited, the package revoked: `full = before + event >= amount` is computed from the event); only the bookkeeping column `refunded_minor` is clamped, by EVERY writer: `refunded_minor = MIN(amount_minor, refunded_minor + ?)`. There is deliberately NO trigger that aborts a refund write: a chargeback arriving after a partial refund would then fail and WE would lose the money. Instead: (1) `test/refund-writers.test.ts` (node project) scans every `UPDATE topups|package_orders SET ... refunded_minor` in `src/core/billing` and fails on one without `MIN(amount_minor, ...)`; (2) the part of an event beyond the charge is recorded per event (`card_refunds.over_charge_minor`, `package_refunds.over_charge_minor`, a `billing_audit` row `refund_exceeds_charge`) and raises the P1 alert `refund_exceeds_charge` for reconciliation; (3) the daily `reconcileRefundBounds` alerts on any order with `refunded_minor > amount_minor` (it should never find one). Writers (all clamped): `card-refunds.ts` settle-confirm, webhook refund / chargeback, our own refund reservation, held-refund debit; `package-orders.ts` yearly refund plan (debt part), full refund / chargeback of an upgrade, full refund / chargeback, partial refund. Cost if wrong: an over-refund is visible only as an alert and a note, not as a refused write; the wallet debit stays the source of truth for the money.


## Daily FX rate (WA-FX-DAILY-1)
Meta bills us in USD; merchants pay from an EGP wallet. The USD->EGP rate is no longer hand-set: the daily cron (`runDailyFx`, called from `scheduled` beside `dailyBilling`, `src/core/billing/fx-daily.ts`, cron `17 1 * * *`, no weekday field so Cloudflare's 1 = Sunday numbering does not apply) appends ONE `fx_rates` row per UTC day (`obs_day`, unique index; `fx_rates` stays immutable). Plan and research: docs/plans/2026-11-12-daily-fx-rate.md.
- **Sources**: fawazahmed0 currency-api (jsDelivr, then its Pages mirror; CC0, no key) primary; open.er-api.com fallback (one call a day). Rates from open.er-api.com are provided by https://www.exchangerate-api.com (attribution required by their terms). Every response is Zod-validated.
- **Row**: `effective_from = now + 24 h` (like every publish, so each workspace copy holds it before it applies); a charge is priced at DELIVERY time, so a lower rate never re-prices an earlier hold (the hold was estimated at the higher rate; the surplus is released). `source`, `vol_bps`, `drift_pct`, `buffer_mode` record how the row was made.
- **Buffer** (`fx-buffer.ts`, pure): `clamp(500, 700, 500 + 1 x max(0, vol - baseline) + 20 x max(0, drift))`; everything is computed over CALENDAR days: vol = stdev of the daily log returns of the last 14 days in bps/day (a return over a gap of d days is divided by sqrt(d)), baseline = trailing-365-day median of it, drift = the 14-day % rise (gap-normalised; only EGP weakening counts); a ONE-day rise above 3% (signed: a fall never counts, a multi-day gap is not a one-day jump) -> 700 at once; it may rise at once but falls at most 50 bps/day and never exceeds 700 (a value above 700, e.g. left by a pin, steps down to 700 at once); fewer than 60 vol windows of history (about 70 days) -> `short_history`, 700. It is stored in `fx_rates.buffer_bps` and ADDS to `pricing_settings.fx_buffer_bps` (the operator's own extra, default 0). **Pin**: `PUT /fx-buffer-pin` (reason, audited) replaces the computed value on every later daily row, any value, until unpinned. A hand publish (`POST /fx-rates`) now REQUIRES `bufferBps` (no silent 0). `GET /fx-rates` lists by effective date, newest first.
- **Fresh feeds only**: a payload dated before yesterday (UTC) (fawazahmed0 `date`, open.er-api `time_last_update_unix`) is a FAILED source and the cron moves to the next one; if all are frozen nothing is inserted and `fx_fetch_failed` fires.
- **Failure**: all sources fail -> the last rate stays, `fx_fetch_failed` (P1). A move over 5% from the newest stored rate is accepted automatically ONLY when the other independent provider (fawazahmed0 vs open.er-api; the jsDelivr and Pages hosts are one feed) is fresh and within 1% of it: it is inserted and `fx_large_move_accepted` (P1) carries both values. Otherwise it is NOT inserted and `fx_rate_rejected` (P1, carries both values) fires; publish by hand if real. Newest observed day (`obs_day`) older than 48 h -> `fx_rate_stale` (P1); this check (`checkFxStale`) runs from `dailyBilling`, NOT from the fetch job, so it still fires when the fetch is what broke.
- **Backfill (one-off, operator, never on deploy)**: `POST /api/v1/operator/fx-backfill {days (default 365, max 400), reason}` loads the dated jsDelivr snapshots of the days BEFORE today into `fx_rates` (`source = backfill`, buffer 700 and mode `backfill`, except the newest: inputs for the buffer, NEVER prices. `pullPricing` skips them, so no workspace copy ever holds one and the first priced row is the first cron row) so the dynamic buffer works from day 1. ONLY the newest inserted row gets the computed buffer (no previous buffer, so no fall limit on day 1; the pin applies). Idempotent (one row per `obs_day`; a re-run inserts only missing days); a day whose snapshot is absent, invalid or dated differently is skipped and counted in `missing`; the 5% band does not apply to history. Cost: `days` fetches plus a few D1 calls, within the 1000 subrequests of a paid Worker. Residual: a backfill makes the newest day on file yesterday, so the staleness clock starts from there.
- **Health**: `GET /health` carries `fxObsDay` (newest observed rate day, `SELECT max(obs_day)`) and `fxAgeHours`, null when unknown; a failing read never fails the probe (always 200). The OS watchdog alerts at `fxAgeHours` > 48, a backstop that does not depend on the cron.
- **Category change**: `meta_adjust` is the new price minus what was CHARGED (`charged_minor`, VAT from the ledger), never a re-price of the old category.
- **Residual**: if the whole cron trigger is dead, both tasks stop and the missing `daily_billing` log line is the only signal. A rate moved by hand through `POST /fx-rates` counts as the newest rate for the band and is skipped by the volatility history (history = cron rows only).
