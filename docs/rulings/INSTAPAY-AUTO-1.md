# Ruling INSTAPAY-AUTO-1 (Chat)

Plan `docs/superpowers/plans/2026-11-14-instapay-auto-confirm.md` (ebda-store PR 759), tasks C1-C8; foundation v0.3.0 (rulings INSTAPAY-1..7 and INSTAPAY-CLEAN-1). Code: `src/core/billing/instapay-auto.ts`, `instapay-reader.ts`, `instapay-notify.ts`, `src/routes/internal-instapay.ts`, D1 `0033_instapay_auto_confirm.sql`. Ships with the mode **off**; `shadow` decides without activating; nothing in this PR turns `live` on anywhere.

**Ruling INSTAPAY-AUTO-1.1 - the model only reads, plain code decides, receipt text is never an instruction.** The reader (`instapay-reader.ts`) fills the foundation's typed extract; `decideInstapay` (pure) decides; the expected amount and the payee come from the server, never from the receipt. Evidence: test `fraud: text injected into the image`, `fraud: wrong handle`, `fraud: amount mismatch`, and the mutation check `reader trusts the raw answer` (killed). Cost if wrong: a receipt that fools the validator confirms one payment (capped at one month of the plan for a first payment) until the owner taps "not received".

**Ruling INSTAPAY-AUTO-1.2 - one decision per request, idempotent, resumable.** `instapay_auto_confirmations.request_id` and `idempotency_key` are UNIQUE; a replay returns the stored row (no second model call, no second grant); an abandoned `pending_decision` is taken over only after a 5 minute lease. Evidence: `top-up, full match, live ... a replay changes nothing`, `an abandoned pending decision is taken over`, `double submit`. Cost if wrong: a stuck decision waits for the daily sweep.

**Ruling INSTAPAY-AUTO-1.3 - one shared D1 (`INSTAPAY_DEDUPE_DB`) is the platform-global duplicate index; fail closed.** A claim is made BEFORE the decision, released only if this call made it and the activation failed, kept when the request waits for a person, burned by a revert. No binding, an index that throws, or an unreadable reference = a duplicate. The per-product unique `bank_ref` index stays as a second layer. Evidence: the foundation contract run against the real D1 (`test/instapay-auto-schema.test.ts`), `fraud: a receipt already claimed by ANOTHER PRODUCT`, 20-concurrent test, mutation `duplicate claim skipped` and the scoped control (unshared index). Cost if wrong: a receipt confirmed in one product could be replayed in the other.

**Ruling INSTAPAY-AUTO-1.4 - clean payment = human-confirmed at once, or auto-confirmed and listed in a digest that was SENT (INSTAPAY-CLEAN-1); no waiting window.** Until then the merchant's next payment above the first-payment cap waits for a person. `digest_sent_at` is stamped only when the brain answers 2xx with `{sent:true}`. Evidence: `INSTAPAY-CLEAN-1 ...`, `stamps digest_sent_at ONLY when ...`, mutations `clean = confirmed` and `digest stamped without sent:true` (killed). Cost if wrong: a merchant's second large payment waits for a person a day longer.

**Ruling INSTAPAY-AUTO-1.5 - revert = back to unpaid with a 48 h grace, unused credits of THAT payment removed, consumed never clawed back, never negative, idempotent per ledger ref.** Top-up: `min(credited, available wallet)`. Package: the unused remainder of the period's grant (`grant:<periodStart>:<package>`), consumed and expired credits stay. The plan stays fully in effect until `payment_unconfirmed_until` and then the period ends there (the revert shortens `period_end` to the grace end; it never lengthens it), so service stops exactly at +48 h unless a new confirmed payment arrives, which clears the marker and queues/starts its period normally. This is a deliberate difference from the 7 day past_due grace (WA-GRACE-1), which stays for every other path. Only the reverted payment's own period is shortened (a payment that did not start the running period raises `instapay_confirmed_not_granted` for a person). Also: reference and image burned, workspace auto-disabled until the owner re-enables it, a repair pass can never grant a reverted payment. Evidence: `test/instapay-auto-revert.test.ts`, 8 mutations killed (`revert does not shorten the plan`, `removes the whole top-up`, `removes consumed AI credits`, `does not burn`, `racing taps all report reverted`, `repair may grant a reverted payment`). Cost if wrong: credits spent from another payment are not protected (the wallet is fungible); a revert on a queued renewal needs a person.

**Ruling INSTAPAY-AUTO-1.6 - only a purchase that STARTS a period is automatic.** A renewal queued behind the running period, an upgrade, a queued switch and any amount at or above the two-approver threshold (`ADJUSTMENT_APPROVAL_MINOR`) always wait for a person, reported as `ABOVE_DUAL_CONTROL_THRESHOLD` (no reason code fits "a person must look at this kind"). Cost if wrong: a few legitimate renewals wait for a person.

**Ruling INSTAPAY-AUTO-1.7 - decision and kill switches are read from D1 on every decision (NEVER-stale, no cache).** `instapay_auto_settings.mode` (default `off`), `instapay_auto_workspace`; `off` and "not ready" (dedupe binding, bridge secret, brain URL, payee handle, AI binding missing) short-circuit before any read or claim; `/health` reports `instapayAuto`. Cost if wrong: none (more waits, never fewer checks).

**Ruling INSTAPAY-AUTO-1.8 - grant failure after the confirm leaves the row `failed` and the request `confirmed`; the daily repair grants it once.** The row is not flipped back to `auto_confirmed` (the foundation lifecycle makes `failed` terminal), so such a payment is not in the digest and has no tap; the P1 alert `instapay_grant_failed` and the operator list are its visibility. Cost if wrong: one repaired payment cannot be reverted with the tap (the operator console refuses it too: not auto-confirmed).

**Ruling INSTAPAY-AUTO-1.9 - the digest runs inside the existing daily pass (01:17 UTC), not a new cron.** The Worker has one cron on purpose; the brain allows one digest per product per UTC day and 200 items, so more than 200 waiting drain over days. Cost if wrong: the owner reads the digest at 03:17-04:17 Cairo time instead of 09:00.

**Ruling INSTAPAY-AUTO-1.10 - the production dedupe D1 binding is NOT in `wrangler.jsonc` in this PR.** The database `ebda-instapay-dedupe` does not exist yet (the Store plan creates it, S1) and a binding to a missing database fails the whole deploy. Auto-confirm is fail-closed without it. At rollout (R1): create it on the personal Cloudflare account, apply `DEDUPE_SCHEMA_SQL`, add `{ "binding": "INSTAPAY_DEDUPE_DB", "database_name": "ebda-instapay-dedupe", "database_id": "<id>" }` to `d1_databases`, set `INSTAPAY_BRIDGE_SECRET` (= the brain's `INSTAPAY_BRIDGE_SECRET_CHAT`) and `BRAIN_BRIDGE_URL`, and set `INSTAPAY_REVERT_URL_CHAT` on the brain to `https://<this worker>/internal/instapay/auto-confirm/not-received`. Cost if wrong: auto-confirm stays off (not ready) until done.

**Ruling INSTAPAY-AUTO-1.11 - the proof reader is declared a Smart Layer path (`capabilities/guard.config.json` `smartLayerPaths`), not a baseline entry.** Baselines may only shrink (ratchet), and Chat has no Smart Layer module yet, so `src/core/billing/instapay-reader.ts` is the one place that calls the vision model for InstaPay: a single schema-constrained extraction (`guided_json`, temperature 0, no tools, no conversational output, answer parsed by the foundation validator and never trusted). Evidence: `test/capability-registry.test.ts` bypass guard green with an unchanged baseline; every other file still fails the guard. Cost if wrong: if the owner does not accept this exemption the reader must move behind the Smart Layer adapter before live.

**Residual (not fixed, documented):** (a) the revert's AI-credit removal reads the grant from the DO ledger; if the entitlement push that grants the period's credits failed AND the owner reverts within minutes, the later grant is not removed (the unused part expires at the shortened period end, so exposure is credits consumed within the 48 h). (b) A person-confirmed payment never registers in the shared index (only the R1 history backfill covers old ones). (c) Two product copies of the revert notice text (foundation has none). (d) The `INSTAPAY_RECEIPT_AI_MODEL` default is the Store's model; real-receipt accuracy is NOT verified (the shadow week measures it).
