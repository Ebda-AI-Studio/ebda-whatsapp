# Ruling PERF-TIMEOUTS-1

**Decision:** every third-party HTTP call in ebda-whatsapp (Meta Graph and the WhatsApp Cloud API, Kashier, the AI provider, Telegram alerts, merchant connectors) goes through `fetchWithTimeout` (`src/core/net/fetch-with-timeout.ts`): payments 10 s, AI 30 s, everything else 8 s by class. A call whose own limit was chosen on purpose passes it as `timeoutMs`, so its behaviour is unchanged: Meta send 15 s, catalog 20 s, templates and numbers 15 s, media lookup 30 s and download 60 s, upload 60 s, the AI call 25 s (or the workspace's own), a connector the lesser of its own limit and the deadline left, Telegram 5 s. The Kashier default transport uses the payment class. The timeout error is named `TimeoutError`, like the platform's own, so the existing `err.name === 'TimeoutError'` checks keep working. It logs the label and the limit only, never a URL, header, body or phone number. `test/no-raw-fetch.test.ts` fails on a raw global `fetch(` or `?? fetch` anywhere under `src/` outside the helper; service bindings, assets and Durable Object stubs (`x.fetch(...)`) are not third-party calls.

**Evidence:** same pattern as the Store (`apps/api/src/lib/fetch-with-timeout.ts`, SCALE-READY #6). Before this, 15 of the 17 call sites each carried their own `AbortSignal.timeout`, and nothing stopped the next one from having none. Local run: 61 test files and 989 tests that import or mock these modules pass.

**Cost if wrong:** a limit set too short turns a slow but successful Meta call into a retried duplicate send (a send already treats a network failure as retryable); the explicit `timeoutMs` values keep today's limits so nothing gets shorter in this change.
