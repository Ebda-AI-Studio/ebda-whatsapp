# Phase 2 messaging core: speed

Targets (plan, Global Constraints): conversation list p95 < 150 ms server time for 50 rows; open chat (last 50 messages) p95 < 150 ms; send → Meta accepted p95 < 1.5 s.

## Measured (local), 2026-10-24
Run: `node scripts/bench-local.mjs` (executes `test/perf.test.ts` inside workerd; no servers, no Docker, no network, no Meta). 5,000 conversations seeded (4 messages each) plus one 2,000-message chat; every call goes Worker → Hono → `requireStoreAccess` (JWT verify, cached JWKS) → Durable Object → SQLite. Milliseconds, 100 runs (25 for the filtered list and search):

| Path | p50 | p95 | max | mean |
|---|---|---|---|---|
| Conversation list, 50 rows | 1 | 2 | 7 | 1.36 |
| Conversation list, unread filter | 1 | 2 | 3 | 1.28 |
| Open chat, last 50 messages (2,000-message chat) | 1 | 2 | 4 | 1.13 |
| Search (FTS5, prefix) | 1 | 1 | 2 | 0.84 |
| Send accept → queued + enqueued (API side) | 2 | 3 | 8 | 1.92 |

Caveats: workerd's clock advances only on I/O, so single readings are whole milliseconds; use `mean`. Local DO calls have no network hop: live figures add the Worker↔DO placement and D1 reads (the workspace lookup and the active-number lookup are D1 reads; the first is cached for 60 s per isolate). Both targets are asserted in tests (`test/perf.test.ts`, `test/inbox-api.test.ts`), so a regression fails the suite.

Why these are fast: keyset pagination on `(last_message_at, id)` with matching indexes (plain, unread-partial, unassigned-partial, assignee), a per-row index lookup for the last message (`messages(conversation_id, id)`), tags fetched in one `IN` query, FTS5 for search, and no per-request fan-out beyond one DO call.
