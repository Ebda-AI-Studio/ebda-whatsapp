## 4. Legal pages (Ahmad approves, Claude drafts)
Privacy policy, terms of service (incl. refund terms), and a **data deletion** URL/instructions page. Meta's app review requires the privacy policy URL and the data deletion URL. The policy and terms live on the Store's public site (ebda.app); **the data-deletion URL is this product's own route** (B9, Ruling LEGAL-DELETE-1): in the Meta app (Settings, Basic, "Data Deletion Request URL") enter `https://wa.ebda.app/meta/data-deletion`.
- `POST /meta/data-deletion` is Meta's callback. It verifies `signed_request` (HMAC-SHA256 of the payload with `META_APP_SECRET`), records the request in D1 `meta_deletion_requests` (the Meta user id is kept only as a hash), answers `{ "url": ".../meta/data-deletion/status?code=<code>", "confirmation_code": "<code>" }` and removes the connections that person authorised (found through `waba_credentials.fb_user_id`, which the browser reports at Embedded Signup; D1 migration `0026_meta_data_deletion.sql`).
- `GET /meta/data-deletion/status?code=<code>` is the page the person can open (HTML, Arabic then English; JSON for a program): `received`, `done` or `needs_review`. `GET /meta/data-deletion` without a code is the instructions page with the support address (`SUPPORT_EMAIL`, pinned to the brand's `supportEmail`).
- A request we cannot match (a connection made before the user id was recorded, or a person who never connected) is never reported as done: it waits for a person and raises the P1 alert `meta_deletion_needs_review` (runbook `docs/runbooks/alerts/`).
- **Not verified against Meta's live callback**: check it with Meta's "Data Deletion Callback" test in the app dashboard on the first real contact (`docs/launch/first-live-contact-checklist.md` when it lands) and record the date here: ______
- **Replay protection.** The signed request must carry `issued_at` no older than 5 minutes (and at most 1 minute in the future) and none of the login-only fields (`code`, `oauth_token`, `access_token`, `expires`, `expires_in`): a signed blob captured from a login flow, or an old deletion request, is `400`. The code is derived from (user id, `issued_at`), so a replay inside the window returns the SAME confirmation code and status URL and runs nothing again (one stored row, one erasure). The erasure is queued, not part of the answer; operators see every request (state and counts only) in the console, Queues tab, or at `GET /api/v1/operator/meta-deletions`.
- Ruling LEGAL-DELETE-1 - the callback erases the person's CONNECTIONS (accounts, numbers, tokens, PINs). Their merchant's customer data is the merchant's and has its own erasure path (`DELETE /contacts/:waId`, workspace deletion). Cost if wrong: a person who is also a customer-data subject of a merchant must go through that merchant; the privacy policy must say so (<!-- PENDING LEGAL REVIEW: data-deletion scope -->).

### InstaPay review duty (operator, while `INSTAPAY_BILLING_ENABLED` is on)
Every InstaPay payment waits for a person: an operator opens **Operator -> Queues -> InstaPay transfers**, views the proof (a signed link that works for 2 minutes), checks the amount and the reference against the bank app, and confirms or rejects with a reason the merchant reads. **SLA: review within 4 business hours (Sunday to Thursday, 09:00-17:00 Africa/Cairo).** A proof that waits longer raises `instapay_proof_overdue` (P1) once. The person who made the request never reviews it; at or above `ADJUSTMENT_APPROVAL_MINOR` two different operators must confirm. A request with no proof expires after 48 hours (daily pass); a proof already uploaded never expires on the clock. Rejection tells the merchant in the Wallet screen (the reason is shown); there is no WhatsApp notification yet because no suitable utility template exists (a template needs Meta approval first).

`INTEGRATOR_TOKENS_ENABLED` (default off; `1` or `true`) lets a merchant's own server call the API with a scoped client token from the sign-in service (identity contract v1.3, DRAFT r2: do not switch it on before the accounts owner has approved the contract and shipped `POST /oauth/token`, the client table and `Accounts.isRevoked` for `cli_` ids). When on: the `ACCOUNTS` binding must be bound (every integration request checks it and fails closed with 503; a 30 s per-isolate cache of an "ok" answer is the only staleness). The scope map is `src/core/identity/scopes.ts`; every write by a server token logs `integration_write { clientId, jti, storeId, scope }`.

### Request guards (security, `src/core/request-guards.ts`, one middleware before every route)
- Body size is checked before the body is read (`Content-Length`) and counted while it is read (chunked, no length): `/meta/webhook` and `/kashier/webhook` 256 KB, JSON API 1 MB, uploads keep their own limits (media 50 MB, imports 10 MB, InstaPay proof 5 MB, plus the multipart envelope). Over: `413 {"error":"payload_too_large"}`.
- Content-type allow-list when a body is present: webhooks and API writes `application/json`; media and imports `multipart/form-data`; the InstaPay proof jpeg/png/webp/pdf. Anything else: `415 {"error":"unsupported_media"}`.
- Public-route limits, token buckets in the isolate (the Workers Rate Limiting binding is not configured): `/t/:code` 20/s (burst 60) per client (IPv6 by /64) AND 200/s (burst 500) per workspace; `/meta/webhook` 50/s (burst 200) per `phone_number_id`, counted only for requests with a VALID signature (a forged body cannot spend another number's allowance). Over: `429 {"error":"rate_limited"}` with `Retry-After`. Staleness class BOUNDED-stale: per isolate, resets on eviction, several isolates each hold a bucket; the limits sit far above real traffic and guard no money or permission. Residual: Meta and Kashier redeliver a 429 with backoff, so a signed event over the limit is delayed, not lost; a number that keeps exceeding the limit keeps being delayed.
  - **Ruling WA-LINK-1 (closed by WA-LINK-2):** tracked-link codes are signed (`<ws>.<random>.<mac>`, HKDF label `tracked-link-code/v1` from `PROOF_URL_SECRET`). The guard verifies the MAC for every method on `/t/` before any bucket or Durable Object, and the route verifies it again; so made-up codes can no longer spend a store's store-wide allowance. Remaining: a flood of GENUINE codes (each signed for a real recipient) is capped per client and per store as before. Cost if wrong: a leaked `PROOF_URL_SECRET` lets anyone mint valid link codes (and proof links); rotating it invalidates EVERY issued tracked link and proof link at once, so rotate only for a leak, and announce it.
- `/t/:code` already answers a malformed code or an unknown workspace with 404 before any Durable Object is woken; after deploy check that a made-up code returns 404 and a normal webhook and API call still pass.

## Media type is checked from the bytes (M-134)
`POST /stores/:storeId/media` compares the first bytes of the file (JPEG, PNG, PDF, MP4 `ftyp`, Ogg `OpusHead`) with the declared type; a mismatch is `415 unsupported_media` and nothing reaches Meta.

## First live contact and the cross-Worker secret (W2-CONTRACT)
- `docs/launch/first-live-contact-checklist.md` lists what to observe on the first real contact with Meta Graph, Embedded Signup and Kashier, and where to record it. Nothing in it is done until the Observed column has evidence.
- **SUITE_BUYER_KEY_SECRET equality (D4).** Each suite Worker publishes `buyerKeyVector` on `GET /health` (only when `SUITE_BUYER_KEY_SECRET` is at least 64 characters, `MIN_PROBE_SECRET_LENGTH`; on a shorter secret the public value would be an offline-guessing oracle, so nothing is published and verify-prod reports SKIP): `HMAC-SHA256(SUITE_BUYER_KEY_SECRET, "suite-buyer-key-probe:v1")` as lowercase hex, first 16 characters (a domain-separated string that is not a phone number, so the public value is nobody's buyer key; the secret never leaves the Worker). `node scripts/verify-prod.mjs --base https://<wa host> --peer-health https://<store api host>/health` compares the two and FAILS when they differ. Ebda Store publishes the same field (Store #285, 2026-10-27; it goes live with the Store's next API deploy); until it does, the check is reported as SKIPPED with that reason, never as passed. Both sides prove the same derivation against the shared test vector `vectors/buyer-key-probe.json` (vendored from the Store, sha pinned in `test/vendored-artifacts.test.ts`).
- **Incomplete `store.plan_changed` (D3).** An event with `includesWhatsApp: true` that lacks `status` or `periodEnd` grants nothing and raises the P1 alert `store_plan_incomplete`; a cancellation (`includesWhatsApp: false`) needs neither. Ruling D3-1 - the Store must send both fields on every grant; the schema keeps them optional so an old event still parses instead of landing in the DLQ. Cost if wrong: a Store build that never sends them leaves every Business-plan merchant without the included package until it does; the P1 alert makes that visible the first time.

## Scale (W2-SCALE)
- **Ruling WA-SCALE-SPLIT-1 - `WorkspaceDO` (about 2,100 lines) is NOT split by concern now; the split is deferred until after launch.** Evidence: the class is one Durable Object with one SQLite database, so a split is a code-organisation change (mixins or delegate modules over the same `ctx`), not a scaling one; it touches every RPC method every test calls and every wave-2 branch that is being written in parallel, and the audit finding (M-158) is about maintainability, not correctness. The rename half of M-158 is done: the review-round test files carry behaviour names (see `git log --follow`). Cost if wrong: the file keeps growing and every wave-2 merge keeps conflicting inside it until the split lands; the split then costs one dedicated, conflict-free window.
- **Ruling WA-SCALE-1 - the backup EXPORT is chunked and streamed; the backup RESTORE is not yet.** `importSnapshot` still reads a whole snapshot into memory and inserts it in one transaction, which is the next ceiling for a very large workspace (it is exercised only by drills and disasters, not nightly). Cost if wrong: restoring a workspace of several hundred thousand rows could exceed Durable Object memory or time; the fallback is restoring tables in separate calls by hand. The 500,000-row spike (`test/scale-spike.test.ts`, BENCH=1, nightly) measures the export and the hot reads at that size.
- **Fixed bench budget (M-176).** Benches no longer take a runner-sized millisecond budget; each measures a same-run baseline and fails over a fixed multiple (`test/helpers/bench.ts`, `BUDGET_RATIO`). `scripts/bench-local.mjs` additionally asserts the 150 ms absolute product budget on a known machine (`BENCH_ABSOLUTE_MS`).
