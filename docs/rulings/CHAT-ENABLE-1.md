# Ruling CHAT-ENABLE-1 (controller, 2026-11-19)

**Decision:** a Chat workspace (the `workspaces` registry row every store route resolves the store through, plus the owner row) is created ONLY by an explicit action of the store's OWNER, through ONE idempotent function, `ensureWorkspace(storeId)` (`src/core/workspace-registry.ts`). Nothing creates a workspace on a visit, on a token, or for an operator.

**The consent path that exists:** the owner/admin's "connect Ebda Chat" action in the Store (`POST /stores/:storeId/whatsapp-link`, which checks the Store admin role, MFA and the plan entitlement, flips the Store's link flag and emits `store.linked` with `ownerUserId`). The Chat queue consumer (`src/core/store-events.ts`) registers the store from that event, but only after the Store confirms LIVE, through the bridge (`memberRole`), that `ownerUserId` is the OWNER of exactly that `storeId`: staff, strangers, an owner of ANOTHER store and a platform super admin are refused (ack + log); the Store unreachable = retry (fail closed); no Store link configured = refused. Any other event never registers a store.
- Events for a store that never enabled Chat do not churn the queue: a non-link event is retried a few deliveries (a `store.plan_changed` can race just behind the `store.linked`), then acknowledged and logged (`store_event_dropped_not_enabled`), never dead-lettered; standing events (suspend/delete) are acknowledged at once.
- The web shell for a store with no workspace shows its own "not enabled" state (not failed-load banners), pointing at the store's Settings in Store admin.

**What enabling starts:** the registry row and the owner row. Nothing else: no charge (money moves only through the plan and wallet flows the owner starts), no plan change (the plan arrives from the Store's own `store.plan_changed`), no trial clock, no message. The only clock is the new-workspace campaign cap (`docs/campaigns.md`: first 14 days after the workspace's Durable Object first runs). The button copy says so.

**Evidence (live bug, 2026-11-19):** prod D1 had zero rows in `workspaces`, `phone_numbers`, `workspace_owners`, `workspace_subscriptions`; every store data route answered 404 (`workspaceStub()`), `/me` answered 200 (it never reads the row), every Store event was retried into the DLQ, a number connect would fail the foreign key (`foreign_keys=1`). Nothing in the code ever created the row ("onboarding registers it", `store-events.ts`, was never built). Tests: `test/workspace-enable.test.ts` reproduces it (404 before the link, 200 after), idempotency, owner-only, cross-store, Store unreachable, no bridge, the FK path of a number connect, the non-churning retry; three mutations killed (owner not checked, no bounded retry, Store-unreachable registers).

**Gap found (Store side, not fixed here):** the Store has no admin UI for the link action; only the API route and the Store assistant tool `notify.whatsapp-link` exist (the legacy WhatsApp page was deleted, WA-LEGACY-1). A "Connect Ebda Chat" card in Store Settings that calls `POST /stores/:id/whatsapp-link` is the Store-side half of this ruling.

**Cost if wrong:** an owner who never finds the Store-side action sees the "not enabled" state and no data; a Store that emitted `store.linked` for a user the bridge cannot confirm (Store outage) is retried, not registered, until the Store answers.
