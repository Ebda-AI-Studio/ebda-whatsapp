# Ruling WA-CAT-5

**Decision:** The ledger (`catalog_items`) records what Meta ACCEPTED, never what we intended: rows are written only after `items_batch` answered ok (`plan().commit()`), so a failed send is planned again from the unchanged ledger. An item the Store sells but we exclude (no image, insecure image, no title) is never "wanted": the end of a full pass deletes it if Meta still lists it (self-healing for a lost DELETE and for items the pre-ledger code pushed). On the event path an excluded item is DELETEd unless the ledger already says `excluded` (a phantom DELETE is harmless); on a full pass a DELETE is sent for a `synced` row and the pass's closing step handles the rest from Meta's real list. An ok-but-empty Store answer for products that just changed archives nothing at once and schedules a full (mass-delete-guarded) pass. The shop-button choice is re-read before each write and before recording, so the merchant's switch wins over a pass that read `want` earlier. One agent turn sends one product message (every `show_products` row of the turn merged, deduplicated, at most 30) plus at most one catalogue message. A retailer id over 64 characters (the Store bridge refuses the whole call for one) is dropped before `getProducts` and reported as unknown, never failing the cart. A cart from another catalogue has its own message.

**Evidence (2026-11-14, independent review of PR 78, comment 6871093784):** I1/M4 (ledger written before Meta accepted, `wanted` counted excluded rows), M1, M3, M5, M6, M7. Tests: `test/catalogue-store.test.ts` ("a failed send never loses a delete or invents a card", "mid-flight wins", "while the pass is writing"), `test/catalogue-chat.test.ts` (one product message per turn, 64-character ids, other-catalogue cart), `test/catalog-sync.test.ts`; each mutation-checked (ledger written before send, `wanted` including excluded, no re-read of `want`, no empty-answer guard, no id filter).

**Cost if wrong:** A phantom DELETE for an item Meta never had costs one request. If the empty-answer guard holds back a genuine mass removal, the item leaves Meta at the next full pass (at most minutes with the soon-scheduled pass) instead of at once. If the merchant's switch and a pass race anyway, the next pass restores the merchant's stored choice (one tap to correct).
