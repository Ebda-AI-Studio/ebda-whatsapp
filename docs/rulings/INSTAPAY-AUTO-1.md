# Ruling INSTAPAY-AUTO-1 (Chat)

Plan `docs/superpowers/plans/2026-11-14-instapay-auto-confirm.md` (ebda-store PR 759), tasks C1-C8; foundation v0.3.0 (rulings INSTAPAY-1..7 and INSTAPAY-CLEAN-1). Code: `src/core/billing/instapay-auto.ts`, `instapay-reader.ts`, `instapay-notify.ts`, `src/routes/internal-instapay.ts`, D1 `0033_instapay_auto_confirm.sql`. Ships with the mode **off**; `shadow` decides without activating; nothing in this PR turns `live` on anywhere.

**Ruling INSTAPAY-AUTO-1.1 - the model only reads, plain code decides, receipt text is never an instruction.** The reader (`instapay-reader.ts`) fills the foundation's typed extract; `decideInstapay` (pure) decides; the expected amount and the payee come from the server, never from the receipt. Evidence: test `fraud: text injected into the image`, `fraud: wrong handle`, `fraud: amount mismatch`, and the mutation check `reader trusts the raw answer` (killed). Cost if wrong: a receipt that fools the validator confirms one payment (capped at one month of the plan for a first payment) until the owner taps "not received".

**Ruling INSTAPAY-AUTO-1.2 - one decision per request, idempotent, resumable.** `instapay_auto_confirmations.request_id` and `idempotency_key` are UNIQUE; a replay returns the stored row (no second model call, no second grant); an abandoned `pending_decision` is taken over only after a 5 minute lease. Evidence: `top-up, full match, live ... a replay changes nothing`, `an abandoned pending decision is taken over`, `double submit`. Cost if wrong: a stuck decision waits for the daily sweep.

**Ruling INSTAPAY-AUTO-1.3 - one shared D1 (`INSTAPAY_DEDUPE_DB`) is the platform-global duplicate index; fail closed.** A claim is made BEFORE the decision and KEPT whatever happens next while the payment can still be confirmed (waits for a person, a person confirmed it in a race, the grant failed); it is released only when the request is rejected (or found rejected/expired in the race) and burned by a revert. A person's confirmation claims it too (I1, numeric bank references; a reference with letters is guarded by the bank_ref unique index alone), and a receipt the index already holds is HELD, never confirmed. `POST /operator/instapay/auto/backfill` burns every already-confirmed reference + image once (idempotent). No binding, an index that throws, or an unreadable reference = a duplicate. The per-product unique `bank_ref` index stays as a second layer. Evidence: the foundation contract run against the real D1 (`test/instapay-auto-schema.test.ts`), `fraud: a receipt already claimed by ANOTHER PRODUCT`, 20-concurrent test, mutation `duplicate claim skipped` and the scoped control (unshared index). Cost if wrong: a receipt confirmed in one product could be replayed in the other.

**Ruling INSTAPAY-AUTO-1.4 - clean payment = human-confirmed at once, or auto-confirmed and listed in a digest that was SENT (INSTAPAY-CLEAN-1); no waiting window.** Until then the merchant's next payment above the first-payment cap waits for a person. `digest_sent_at` is stamped only when the brain answers 2xx with `{sent:true}`. Evidence: `INSTAPAY-CLEAN-1 ...`, `stamps digest_sent_at ONLY when ...`, mutations `clean = confirmed` and `digest stamped without sent:true` (killed). Cost if wrong: a merchant's second large payment waits for a person a day longer.

**Ruling INSTAPAY-AUTO-1.5 - revert = back to unpaid with a 48 h grace, unused credits of THAT payment removed, consumed never clawed back, never negative, idempotent per ledger ref.** Top-up: `min(credited, available wallet)`. Package: the unused remainder of the period's grant (`grant:<periodStart>:<package>`), consumed and expired credits stay. The plan stays fully in effect until `payment_unconfirmed_until` and then the period ends there (the revert shortens `period_end` to the grace end; it never lengthens it), so service stops exactly at +48 h unless a new confirmed payment arrives, which clears the marker and queues/starts its period normally. This is a deliberate difference from the 7 day past_due grace (WA-GRACE-1), which stays for every other path. Only the reverted payment's own period is shortened (a payment that did not start the running period raises `instapay_confirmed_not_granted` for a person). Also: reference and image burned, workspace auto-disabled until the owner re-enables it, a repair pass can never grant a reverted payment. Evidence: `test/instapay-auto-revert.test.ts`, 8 mutations killed (`revert does not shorten the plan`, `removes the whole top-up`, `removes consumed AI credits`, `does not burn`, `racing taps all report reverted`, `repair may grant a reverted payment`). Cost if wrong: credits spent from another payment are not protected (the wallet is fungible); a revert on a queued renewal needs a person.

**Ruling INSTAPAY-AUTO-1.6 - only a purchase that STARTS a period is automatic.** A renewal queued behind the running period, an upgrade, a queued switch and any amount at or above the two-approver threshold (`ADJUSTMENT_APPROVAL_MINOR`) always wait for a person, reported as `ABOVE_DUAL_CONTROL_THRESHOLD` (no reason code fits "a person must look at this kind"). Cost if wrong: a few legitimate renewals wait for a person.

**Ruling INSTAPAY-AUTO-1.7 - decision and kill switches are read from D1 on every decision (NEVER-stale, no cache).** `instapay_auto_settings.mode` (default `off`), `instapay_auto_workspace`; `off` and "not ready" (dedupe binding, bridge secret, brain URL, payee handle, AI binding missing) short-circuit before any read or claim; `/health` reports `instapayAuto`. Cost if wrong: none (more waits, never fewer checks).

**Ruling INSTAPAY-AUTO-1.8 - a payment the SYSTEM confirmed always ends `auto_confirmed` once it is granted (review I3).** A grant that fails after the confirm (or an isolate that dies there) leaves the row `pending_decision`, never `failed`; the daily repair grants it and the sweep (which runs whatever the mode, because the money already moved) ends the row `auto_confirmed` with the confirm time, so it is in the digest and "not received" works. A take-over of such a row finishes the activation instead of re-deciding. Only an offboarded workspace (nothing can be granted) ends `failed`. Evidence: `I3: a grant that fails after the confirm ...`, `I3: a take-over ...`; mutants `I3 stuck rows not swept`, `I3 take-over re-decides` killed. Cost if wrong: a stuck row waits one daily pass.

**Ruling INSTAPAY-CAP-1 - the first-payment cap is cumulative and checked atomically (reviews I5, N2).** Until the workspace has a clean payment, the sum of auto-confirmed amounts not yet seen in a sent digest (and not reverted) plus this payment must be at most one month of the plan; otherwise a person decides. The sum is part of the confirm UPDATE itself (`autoConfirmClaimSql`, `?9` = the month), so concurrent decisions of one workspace cannot all pass a sum read before any of them wrote; losing the cap at write time = `needs_human [FIRST_PAYMENT_OVER_CAP]`, the claim kept. Extra evidence: `five 200 EGP proofs ... decided concurrently`; mutant `N2 cap not in the write` killed. Evidence: `three 200 EGP top-ups under a 500 EGP plan month: two confirm, the third waits`; mutant `I5 cap not cumulative` killed. Cost if wrong: a merchant's third small payment in a day waits for a person until the digest is sent.

**Ruling INSTAPAY-REVERT-1 - a top-up revert removes max(0, min(reverted amount - spend recorded since that top-up, available balance)) (reviews I6, N1).** "Spend" is CONSUMPTION only (`meta_charge`, `meta_adjust`, `ai_charge`): another revert's removal, an operator adjustment, a refund or a chargeback is not this money being used (`two 300 EGP auto top-ups, both reverted: 600 removed`; mutant `N1 any debit counts as spend` killed). Spend after the reverted top-up counts against it first, so money that arrived later (a card top-up) is never taken; the balance only caps the result. Evidence: `200 auto top-up, 150 spent, then a 500 card top-up: the revert removes 50`; mutant `I6 later money counted` killed. Cost if wrong: a merchant who spent from an older balance keeps up to that much of a not-received top-up (bounded by the reverted amount).

**Ruling INSTAPAY-AUTO-1.13 - claims are recoverable and the backfill is paged (reviews M7, N3).** The read reference is written on the decision row BEFORE the claim and is never wiped by a later finalize, so a reject or an expiry (both release, same rule) can free the claim even if the decision died right after claiming; the backfill burns at most 200 rows per call and returns a cursor (`next`) to call again, so one call stays far under the Workers subrequest limit. Evidence: `a request that expires gives back ...`, `a decision that dies right after its claim ...`, `the backfill returns one bounded page and a cursor ...`; mutants killed (the `SELECT ... LIMIT` mutant is equivalent for the subrequest bound, the burn loop's page bound is the one that matters and is killed). Cost if wrong: an operator calls the backfill a few more times.

**Ruling LOCK-UPSTREAM-1 (controller) - CI cannot read the private foundation repo, so a lock + vendored-file co-edit is caught by review, not CI.** `test/foundation-lock-tag.test.ts` proves the lock tag/commit match the vendored package offline and resolves the tag with git only when a local foundation checkout exists. Cost if wrong: a hand-edited lock and vendored copy that agree with each other pass CI until a reviewer or a local run catches it.

**Ruling INSTAPAY-AUTO-1.12 - a package is due at the ORDER amount (review I4).** The expected amount is the order's (`instapay_requests.amount_minor`, what the merchant was told and what the grant checks); if the live price moved since the order was written, the request waits for a person with `AMOUNT_MISMATCH`. Evidence: `the price moved after the order ...`; mutant `I4 price drift ignored` killed (the mutant `expected from plan again` is equivalent while the drift check stands). Cost if wrong: a few orders written just before a price change wait for a person.

**Ruling INSTAPAY-AUTO-1.9 - the digest runs inside the existing daily pass (01:17 UTC), not a new cron.** The Worker has one cron on purpose; the brain allows one digest per product per UTC day and 200 items, so more than 200 waiting drain over days. Cost if wrong: the owner reads the digest at 03:17-04:17 Cairo time instead of 09:00.

**Ruling INSTAPAY-AUTO-1.10 - the production dedupe D1 binding is NOT in `wrangler.jsonc` in this PR (review M8, checked 2026-11-14: `wrangler d1 list` on the personal account has no dedupe database and the Store branch binds none).** The database `ebda-instapay-dedupe` does not exist yet (the Store plan creates it, S1) and a binding to a missing database fails the whole deploy. Auto-confirm is fail-closed without it. At rollout (R1): create it on the personal Cloudflare account, apply `DEDUPE_SCHEMA_SQL`, add `{ "binding": "INSTAPAY_DEDUPE_DB", "database_name": "ebda-instapay-dedupe", "database_id": "<id>" }` to `d1_databases`, set `INSTAPAY_BRIDGE_SECRET` (= the brain's `INSTAPAY_BRIDGE_SECRET_CHAT`) and `BRAIN_BRIDGE_URL`, and set `INSTAPAY_REVERT_URL_CHAT` on the brain to `https://<this worker>/internal/instapay/auto-confirm/not-received`. Cost if wrong: auto-confirm stays off (not ready) until done.

**Update 2026-11-17 (1.10):** the binding PR exists as a DRAFT (branch `fix/instapay-dedupe-binding`; `wrangler.jsonc` carries the placeholder id `00000000-0000-0000-0000-000000000000` and `BRAIN_BRIDGE_URL`). Rollout order: (1) create the D1 and apply `DEDUPE_SCHEMA_SQL`; (2) put the real id in that PR (and the Store PR, repo variable `EBDA_INSTAPAY_DEDUPE_D1_ID`) and merge both; (3) set the secrets. Never merge it with the placeholder: the deploy would fail on the missing database.

**Ruling INSTAPAY-AUTO-1.11 - TEMPORARY, narrow Smart Layer exemption for the proof reader, expires 2026-12-15 (controller decision).** Exactly one file and one function: `src/core/billing/instapay-reader.ts`, `readProofForAutoConfirm`, recorded in `capabilities/guard.config.json` (`smartLayerPaths` for the guard, `smartLayerExemptions` with reason, expiry and follow-up; the guard schema has no expiry field, so `test/smart-layer-exemption.test.ts` checks it). Reason: extraction-only (one schema-constrained read, `guided_json`, temperature 0, no tools, no conversational output), typed output, plain code decides (`decideInstapay`; the answer is validated by the foundation parser and never trusted, receipt text is never an instruction), and the Smart Layer adapters are not merged yet. No baseline grew (ratchet ok). Follow-up (register): move the receipt reader behind the Smart Layer extraction path, then delete the entry. Evidence: bypass guard green with an unchanged baseline; every other file still fails it; the expiry test fails the build after 2026-12-15 until the entry is removed or renewed by a new ruling. Cost if wrong: until the follow-up lands, one file can call the model outside the Smart Layer's controls (no tools, no side effects, output only ever read by the validator).

**Residual (not fixed, documented):** (a) the revert's AI-credit removal reads the grant from the DO ledger; if the entitlement push that grants the period's credits failed AND the owner reverts within minutes, the later grant is not removed (the unused part expires at the shortened period end, so exposure is credits consumed within the 48 h). (b) A person-confirmed payment with a non-numeric bank reference is not in the shared index (letters cannot be a key). (c) Two product copies of the revert notice text (foundation has none). (e) M9's invalid-bank-reference branch is defensive: the foundation's reference shape (6-40 digits) always fits the bank_ref column, so no test can reach it; it is labelled `instapay_auto_error` (where `bank_ref_invalid`), not an amount alert. (d) The `INSTAPAY_RECEIPT_AI_MODEL` default is the Store's model; real-receipt accuracy is NOT verified (the shadow week measures it).
