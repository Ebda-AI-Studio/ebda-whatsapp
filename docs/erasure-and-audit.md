# Erasure record and audit log (W2-ERASE: B3, T8, M-093)

## The erasure record (B3)
`DELETE /api/v1/stores/:id/contacts/:waId` erases a person's rows from the workspace (`eraseContact`). Before it does, it writes an **erasure record** in D1 (`erasure_records`): the workspace id, a **keyed hash** of the person (HMAC-SHA-256 over `workspace:waId`, key HKDF-derived from `TOKEN_ENC_KEY`, label `erasure-subject/v1`, 128 bits) and the time. The table holds no phone number and the hash is bound to the workspace.

It lives in D1 on purpose: a disaster-recovery restore replaces the Durable Object, so a record kept only there would be lost with it.

**Two stamps (no clock race).** `erased_at` is written BEFORE the Durable Object deletes; `completed_at` is written AFTER `eraseContact` returned, from the Durable Object's own clock. Both are needed: a backup taken between the two still holds the person.

**Restore rule.** `importSnapshot` verifies the backup (counts, checksums) and then drops EVERY person who has an erasure record, except one whose oldest message in the backup is newer than `completed_at` (they wrote again after the erase finished: a genuine new relationship). The backup's own time is not compared with anything. A record whose erase never reported finishing (`completed_at` NULL) is dropped always. Dropped: the contact, conversation, messages, status events, notes, tags, orders, campaign rows, `store_state` keys (`away:<wa_id>`) and the uploads of their messages; the result carries `erasedSkipped`. A contact imported from a CSV after the erase (no messages yet) is dropped from an old restore and has to be re-imported. If records exist but cannot be applied (no `TOKEN_ENC_KEY`), the restore refuses instead of guessing.

**One list, two users.** `src/core/erasure-targets.ts` (`ERASURE_TARGETS`: table, and how its rows tie to the person) is what `eraseContact` deletes through AND what `dropErased` filters a backup through, so they cannot drift. `test/erasure-record.test.ts` walks the Durable Object schema and fails if a table holding `wa_id`, `contact_id`, `conversation_id`, `wamid` or `message_id` is in neither `ERASURE_TARGETS` nor `ERASURE_EXEMPT` (which carries the reason, e.g. the money records that stay).

**Ruling ERASE-ORDER-1 - the record is written BEFORE the erase, and a failure to write it never blocks the erase.** A data-protection request must go ahead; a failed record raises `erasure_record_failed` (P1) so a human re-runs the erase (idempotent) and the record. Cost if wrong: between a failed record and its repair, a restore could bring that person back.

**Ruling ERASE-HASH-1 - the subject hash is keyed (HMAC), not a plain hash of the phone number.** Phone numbers are low-entropy; a plain hash would be reversible by enumeration. Cost if wrong: rotating `TOKEN_ENC_KEY` changes every hash, so old records stop matching; the rotation procedure (W2-DR) must re-derive them or keep the old key readable.

When a workspace is deleted (OFFBOARD-1) its `erasure_records` go with it: add the table to `OFFBOARD_TABLES.delete` in `src/core/ops/offboarding.ts` when the two branches meet (the schema walk in `test/offboarding.test.ts` fails until you do).

## The audit log (T8)
Append-only D1 table `audit_log` (triggers forbid UPDATE and DELETE): `at, workspace_id, actor, actor_role (owner|staff|operator|integration|system), action, target_type, target_id, detail, status`.
- **What is recorded**: every state-changing call (not GET/HEAD) under `/api/v1` that ends below 400 or with 403, by one middleware (`auditWrites`, `src/core/audit.ts`), AND every write that `requireStoreAccess` refuses with 403 before a handler runs (a revoked session, a suspended workspace, a non-member, an integration outside its scope): the guard calls `recordAudit` itself with the verified actor, the ROUTED pattern and the status, never a body. Reads that are denied are not recorded (volume). `action` is the route pattern (`POST /stores/:storeId/conversations/:conversationId/assign`), so it names the thing done without any content. The target is the first route parameter besides the workspace.
- **What is never recorded**: request bodies, message text, reason text, phone numbers. `recordAudit` drops a `detail` key named `reason`, `note`, `text`, `message` or `body` (and `test/audit-review.test.ts` scans every call in `src`). An operator's free-text reason (the data-subject export) goes to the deletable D1 table `audit_reasons` (workspace, actor, action, reason; no masking: it is deletable and removed with the workspace), which a workspace deletion removes; the append-only log keeps the structured facts only. A `waId` target (or any phone-shaped value) is stored as its keyed hash.
- **Not recorded for volume**: message sends, mark-as-read and media uploads (the content they touch is already in the workspace).
- Operator calls are recorded too (alongside the older `operator_actions`, `billing_audit`, change log, which keep their own detail).
- Read view: `GET /api/v1/operator/audit-log?workspaceId=&actor=&action=&before=&limit=` (super admin, newest first, `before` = the smallest id seen) and the **Action log** tab of the operator console.

**Ruling AUDIT-OPEN-1 - a failed audit write never fails the action; it raises `audit_write_failed` (P1).** The Worker log line `{audit:"action"}` still names it. Cost if wrong: an action during a D1 outage has no row.

**Ruling AUDIT-SKIP-1 - sends, reads and uploads are not audited.** They are the product's volume; who sent a message is on the message (`author`). Cost if wrong: an abusive staff member's sends are not in this log, only in the workspace.

Retention: see Ruling AUDIT-RETENTION-1 below.

**Ruling AUDIT-RETENTION-1 - `audit_log` is kept 5 years (`AUDIT_RETENTION_YEARS`), then purged by ONE controlled batch; a workspace deletion pseudonymises the merchant's user ids in it.** Five years is the usual horizon for financial evidence (tax and dispute limitation in the markets we sell in); the lawyer review may lengthen or shorten it. *Purge*: the append-only triggers forbid UPDATE and DELETE, so the only way to remove a row is `purgeAuditStatements` (`src/core/ops/audit-retention.ts`), run by an operator through `POST /api/v1/operator/audit-log/purge {reason}` (super admin; reason of 5+ characters), quarterly. It is ONE D1 batch (one transaction): drop both triggers, `DELETE FROM audit_log WHERE at < now - 5 years`, write its own `billing_audit` entry (`audit_log_purged`: actor, reason, cutoff), re-create both triggers. If any statement fails the whole batch rolls back and the triggers stay (`test/audit-review.test.ts`). The same SQL can be run by hand with `wrangler d1 execute` if the route is unavailable (print it from the function; never run a bare `DROP TRIGGER`). *Offboarding*: in the deletion's `d1` batch, rows with `actor_role` owner or staff for that workspace get `actor = <pseudonym>` (the HMAC pseudonym the money tables use), through the same drop / update / re-create sequence inside the batch. Operators (ours) and integration clients keep their ids; the workspace id stays opaque (OFFBOARD-AUDIT-1). Cost if wrong: for up to 5 years an audit row can be linked back to a person only through the Store's own user table; a regulator who wants shorter retention needs only a change of the constant and one purge run.

**Ruling AUDIT-REASONS-1 - NO append-only table holds text a person typed. The reason goes to `audit_reasons` (deletable; removed with the workspace on offboarding) and the immutable row carries `reason_id`.** The class, not one table: `audit_log` (`detail` keys), `offboarding_log`, `operator_actions`, `billing_audit`, `instapay_releases`, `pricing_settings`, `workspace_pricing_overrides`, `operator_view_log` (0027, the view-as trail) (D1 migrations 0022 to 0024 and 0027 add `audit_reasons` and a `reason_id` to each). Mechanics (`src/core/audit-reason.ts`): the reason row is inserted immediately before the immutable row in the same batch and the row takes `last_insert_rowid()`; the old `reason` column is never written with text (the constant `see reason_id` where it is NOT NULL, NULL elsewhere); `billing_audit.ref` (new) holds the structured keys the "once per order / transaction" checks used to keep in `reason`; `before_json` / `after_json` pass through `stripText`, which drops `reason`, `note`, `text`, `message`, `body` keys, so a DTO that carries a reason cannot smuggle it in. The operator screens (change log, pricing history, a workspace's recent actions, the offboarding log) read the text through `LEFT JOIN audit_reasons`, so they show it while the workspace exists and show nothing for a deleted one. No masking is attempted anywhere (a phone mask also eats dates such as 2026-10-27). Guards: `test/guards.test.ts` finds every append-only table from the migrations' triggers and fails if any `INSERT` in `src` names a free-text column (`reason` is allowed only beside `reason_id`); `test/immutable-reasons.test.ts` and `test/offboarding-log-text.test.ts` send a reason with a phone number through every path and look in every append-only table; the `recordAudit` guard above still applies. The request row `offboarding.reason` is cleared when the deletion finishes or is cancelled.
*Pre-launch residual (rows written BEFORE this change keep their text; the tables are immutable by design).* Production has no real operator data yet, so nothing is scrubbed. If text with personal data was ever written, a ONE-TIME controlled scrub is the same sequence as the audit purge (`src/core/ops/audit-retention.ts`), run by an engineer and reviewed by a second person, as ONE D1 batch (so a failure leaves the triggers in place): drop the table's two triggers; for each row with legacy text, insert the text into `audit_reasons` (workspace scope or `_platform`) and set `reason_id` to that row while overwriting `reason` with `see reason_id`; re-create the triggers; record the scrub in `billing_audit`. Cost if wrong: until such a scrub, an operator reason typed before this change (or text a future writer smuggles past both guards) stays in an immutable trail.

**Ruling ERASURE-KEY-1 - the erasure subject hash, the offboarding pseudonym and the audit target ids are keyed by `ERASURE_HMAC_KEY`, a dedicated secret that is never rotated, NOT by `TOKEN_ENC_KEY`.** A hash that followed the rotated key would match no old erasure record, so `dropErased` would let a restore resurrect erased customers, and an offboarding that spans a rotation would write two pseudonyms. The key is in `REQUIRED_SECRETS` (`/health` fails loud when missing), at least 32 characters, seeded at the first deploy. Pre-launch: no erasure record exists yet, so nothing needs re-keying. The offboarding pseudonym is stored once (`pseudonym = coalesce(pseudonym, ?)`) and a retry reuses the stored one. Tests: `test/erasure-record.test.ts`, `test/offboarding-review.test.ts`. Cost if wrong: losing or changing the key orphans every erasure record (a restore brings erased people back until each is erased again), so it is backed up with the other secrets and never touched.

**Ruling STORE-ROUTES-OWNER-1 - every store-route WRITE (`POST/PUT/PATCH/DELETE /stores/:storeId/...`) is refused (403 `operator_route_required`) to a platform super admin who is not a member of that store; reads need view-as (final review I3): header `X-View-As-Merchant: 1` plus a reason, else 403 `view_as_required`.** One check in `requireStoreAccess`, so a route added later is covered by default; `test/store-routes-owner.test.ts` walks every registered store write route. Erasing a contact (the only operator use case among retention / erase / merge / rename) has the operator route `DELETE /api/v1/operator/workspaces/:id/contacts/:waId {reason}`: the reason is required and kept in `audit_reasons`, the erasure record is written like the owner's, the audit row carries the keyed hash of the person. Merge, rename and retention have no operator route (not needed). The owner's `DELETE /stores/:id/contacts/:waId` is owner-only. A super admin who IS a member of the store keeps the platform role on its routes (the existing ruling: they may erase), so the rule is about NON-members. Cost if wrong: an operator who needs to change a store's data on a merchant's behalf has no console action for it (merge, rename, retention) and asks the owner or the engineers; this is intended.

## Operator session check (review)
Every operator request, GET included, re-checks that the session was not revoked, and an unreachable accounts service refuses it (503). Only the reads named in `OPERATOR_READS_WITHOUT_SESSION_CHECK` (src/routes/operator.ts: global price configuration and the platform template catalogue, each with its reason) skip it; a new route is checked by default and `test/operator-session.test.ts` walks every registered operator route to prove it. On the store side the decision is made on the ROUTED pattern (`routePath`), never on the raw URL (an encoded `/expor%74` reaches the same handler): the suspension allow-list (`allowedWhileSuspended`), the integration scope (`gateForRoute`) and the session re-check all take the pattern. Writes always re-check the session; of the READS, `SESSION_CHECKED_READS` (the export) re-check it too, and every other store read is named in `SESSION_UNCHECKED_READS` with its reason in `src/core/identity/scopes.ts`; `test/route-decisions.test.ts` fails when a read route is on neither list. **Ruling READ-SESSION-1**: checking EVERY store read was considered and rejected: it would put the accounts service on every inbox page load and take the inbox down with it. Cost if wrong: a revoked staff session can still READ the inbox for up to the token lifetime: **15 minutes** for a person token (the identity contract's bound on claim staleness, `docs/contracts/identity-v1.3-integrator-tokens.md`) and 10 minutes for an integrator token. Writes, money and the export are never in that window.

## Standalone workspaces: what the audit log records (CHAT-SA-8)
`workspace.created`, `invite.minted`, `invite.consumed`, `invite.revoked` (ids and code hashes only, never a plain code), and later `member.added` / `member.removed`. Invite codes are stored as a keyed hash (HKDF from `ERASURE_HMAC_KEY`, its own `info`), single use, at most 30 days; the plain code is shown to the operator once.
